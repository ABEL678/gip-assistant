# MASTER_PIPELINE — сквозной пайплайн обработки исходников

> **Назначение:** единая карта от загрузки файла до ревизий.
> Заменяет разрозненные заметки о парсинге, LLM, связывании и агентах.
>
> **Версия:** 1.0
> **Обновлено:** 25.10.2026

---

## 1. Обзор

MASTER_PIPELINE — это 7-шаговый конвейер, который превращает сырой
файл (Excel / PDF / DOCX) в утверждённые ГИПом элементы онтологии
(Premise → Goal → Decision → Task) и обратно в ревизию проекта.

```
[Загрузка] → [Парсинг] → [Извлечение LLM] → [Связывание] → [Валидация] → [Агент] → [Ревизии]
```

Каждый шаг — отдельная подсессия (или группа подсессий).
Пайплайн ориентирован на веху 1 (MVP онтологии) + веху 4 (агенты).

---

## 2. 7 шагов

### Шаг 1 — Загрузка (Upload)

**Вход:** пользовательский файл (Excel, PDF, DOCX).
**Выход:** файл сохранён в БД (`Document` + `DocumentVersion`).

- Drop zone на канвасе (уже есть, веха 1 / 6.5).
- Загрузка — через роуты (загрузка файлов) + `DocumentService.create()`.
- `DocumentVersion.file_path` → путь к загруженному файлу.
- `DocumentVersion.text_content` — появится в 6.13a.

**Где описано:** `ARCHITECTURE.md §2.3`, `DOMAIN.md §7.1 / §3.5`.

---

### Шаг 2 — Парсинг (Parsing)

**Вход:** `DocumentVersion.file_path`.
**Выход:** `DocumentVersion.text_content` (чистый текст).

- Excel: уже работает (универсальный парсер из Этапа 1).
- PDF: `PyMuPDF` — извлечение текста.
- DOCX: `python-docx` — извлечение текста.
- Результат → `DocumentVersion.text_content` (TEXT, не JSONB).

**Дельта-подсессия 6.13a:** парсинг PDF/DOCX + поле `text_content`.

---

### Шаг 3 — Извлечение LLM (LLM Extraction)

**Вход:** `DocumentVersion.text_content`.
**Выход:** набор доменных сущностей (Premise, Goal, Decision, Task).

- `RuntimeLLMAdapter.generate()` — промпт с онтологией из `DOMAIN.md` (§2 «Механизм вывода двухуровневый», §9.1 «LLM»).
- Модель возвращает JSON → маппинг в доменные объекты.
- Создаются через `PremiseService.create()`, `GoalService.create()` и т.д.
- `Premise.source_document_id` → связь с DocumentVersion.

**Где описано:** `ARCHITECTURE.md §7.5`, `DOMAIN.md §2 / §9.1`.

---

### Шаг 4 — Связывание (Linking)

**Вход:** доменные сущности из шага 3.
**Выход:** Document ↔ Premise связи.

- `PremiseService.link_document(premise_id, document_id)` — метод сервиса.
- Связь: FK `documents.premise_id` (по `DOMAIN.md §3.5`).
- Обратная связь: `DocumentLink` для документов между собой.

**Дельта-подсессия 6.13b:** `PremiseService.link_document()`.

---

### Шаг 5 — Валидация (Validation)

**Вход:** извлечённые сущности с `verification_status`.
**Выход:** подтверждённые ГИПом сущности.

- GUI: `PremiseCard` — кнопка «Подтвердить» / «Отклонить».
- `GoalCard` — кнопка «Проверить» (уже есть).
- `RuleBasedGoalValidator` (правила 1–6); `GoalValidatorService` — ABC-порт.
- Статусы: `CONFIRMED` / `NOT_CONFIRMED` / `REQUIRES_CHECK` / `NO_DATA`.

**Дельта-подсессия 6.13c:** валидация в GUI.

---

### Шаг 6 — Агент (Agent)

**Вход:** подтверждённые сущности + данные проекта.
**Выход:** автономные действия агентов (RFI, сроки, эскалация).

- **Агент RFI (6.12e):** `list_overdue`, эскалация, лог действий.
- **gip-mcp-gateway (6.12f):** отдельный FastAPI-контейнер, MCP-протокол,
  Tools для агента RFI.
- Цепочка (ARCHITECTURE.md §7.6): агент → MCP → `gip-mcp-gateway` →
  **Agent Gateway** → Существующий API.
- Периметр данных: `DOMAIN.md §9.2.1`, `RULES.md §12.5`.

**Порядок:** 6.12e → 6.12f.

---

### Шаг 7 — Ревизии (Revisions)

**Вход:** изменения в документах (новые версии).
**Выход:** `Revision` + `RevisionDiffPanel`.

- `RevisionService.create()` — при новой версии документа.
- `RevisionDiffPanel` — сравнение версий (UI).
- История всех изменений проекта.

**Дельта-подсессия 6.13d:** доработка `RevisionDiffPanel`.

### 2.1. Технологический стек

| Шаг | Backend-зависимости | Frontend-компоненты |
|-----|---------------------|---------------------|
| 1. Загрузка | `fastapi.FileResponse`, `aioboto3`* (MinIO/S3) | DropZone, FileUpload |
| 2. Парсинг | `PyMuPDF`*, `python-docx`*, `pandas` + `openpyxl` | — |
| 3. Извлечение LLM | `LLMProviderPort`* + `QwenAdapter`* / `OpenAICompatibleAdapter`* | — |
| 4. Связывание | `PremiseService.link_document()` | — |
| 5. Валидация | `RuleBasedGoalValidator` (правила 1–6) | PremiseCard, GoalCard |
| 6. Агент | `gip-mcp-gateway` (отдельный контейнер) | — |
| 7. Ревизии | `RevisionService`, `RevisionDiff` | RevisionDiffPanel |

\* Требуют согласования (AGENTS.md — новые зависимости).
