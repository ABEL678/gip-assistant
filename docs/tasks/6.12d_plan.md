## 1. Цель и критерии готовности

**Цель:** дать ГИПу экран RFI: список запросов, предложения системы,
создание (вручную и из предложения), редактирование, удаление, эскалация.

**Критерии готовности (DoD):**

1. Маршрут `/projects/:id/rfis` открывает страницу RFI.
2. Страница показывает список RFI проекта и блок «Предложенные RFI».
3. Из предложения `action="create"` RFI создаётся не более чем в 3 клика.
4. Причина в форме выбирается не более чем в 2 клика (тип → значение),
   XOR гарантирован одним зависимым `Select` (ручная проверка, тест-раннера нет).
5. Ручное создание: заголовок, причина (решение / цель — строго одна),
   срок `rfi_due_date`, состояние.
6. Редактирование и удаление работают; список инвалидируется после мутаций.
7. Просроченный RFI визуально выделен красным сроком; связи с вводными
   видны как подписи (до 3 + «+N»).
8. Утверждённое/эскалированное предложение не приводит к повторному
   действию: скрывается локально до обновления списка.
9. На `ProjectPage` есть секция «RFI» со счётчиком и переходом.
10. `npm run build` и `npm run lint` — зелёные.
11. Новых зависимостей нет.

## 3. Фактический backend-контракт (6.12c)

Роутер: `backend/src/adapters/api/routes/rfis.py`, prefix `/api`.
HTTP-клиент фронта уже имеет `baseURL="/api"` → пути в клиенте без `/api`.

| # | Метод | Путь | Body / параметры | Ответ |
|---|---|---|---|---|
| 1 | GET | `/projects/{project_id}/rfis/proposals` | — | `200 RfiProposal[]` |
| 2 | POST | `/projects/{project_id}/rfis/from-proposal` | `RfiProposalApprove` | `201 RfiRead`, `400`, `409`, `422` |
| 3 | GET | `/projects/{project_id}/rfis` | — (без пагинации/фильтров) | `200 RfiRead[]` |
| 4 | POST | `/projects/{project_id}/rfis` | `RfiCreate` | `201 RfiRead`, `400`, `409`, `422` |
| 5 | GET | `/rfis/{rfi_id}` | — | `200 RfiRead`, `404` |
| 6 | PATCH | `/rfis/{rfi_id}` | `RfiUpdate` (`exclude_unset`) | `200 RfiRead`, `400`, `404`, `409` |
| 7 | DELETE | `/rfis/{rfi_id}` | — | `204`, `400` |
| 8 | POST | `/rfis/{rfi_id}/escalate` | — (без body) | `200 RfiRead`, `400` |

**Важные свойства контракта (влияют на UI):**

1. `RfiState` — `StrEnum` со значениями **в нижнем регистре**: `open`, `sent`,
   `answered`, `registered`, `closed`, `escalated`. В JSON — lowercase.
2. `RfiRead.status` — `TaskStatus` в **UPPER_SNAKE** (`NOT_STARTED`, …).
   В одном объекте два разных регистра — словари лейблов не смешивать.
3. `RfiRead` **не содержит** `description`, `Document`-ответа, Actions.
   Есть только `premise_ids: list[UUID]`.
4. `RfiCreate.title` обязателен (`min_length=1, max_length=1000`).
5. `RfiCreate`/`RfiUpdate` **не содержат** `description`.
6. `RfiUpdate` использует `None`-sentinel: `None` = «не менять».
   Нельзя очистить `rfi_cause_*` и нельзя сменить тип причины за один PATCH
   (`decision → goal` даёт `400` из-за XOR-ревалидации после применения).
   По той же причине нельзя очистить `rfi_due_date`.
7. `DELETE` и `escalate` на отсутствующем RFI отдают **400**, не 404.
8. `escalate` не проверяет состояние — успешен даже для `closed`,
   повторная эскалация даёт `200` без видимого эффекта.
9. `from-proposal` требует `rfi_cause_decision_id` (обязателен) и
   `rfi_due_date` (обязателен). В `RfiProposal` поле называется
   `reason_decision_id` — нужен маппинг.
10. `RfiProposal.id` — детерминированный `uuid5` (`rule:formulation:existing_rfi_id`),
    не id RFI; в DTO объявлен nullable, но сервис заполняет всегда.
    Для `action="escalate"` id существующего RFI — в `existing_rfi_id`.

### 5.2 `frontend/src/hooks/useRfis.ts`

| Хук | Ключ запроса / инвалидация |
|---|---|
| `useRfis(projectId)` | `["rfis", projectId]`, `enabled: !!projectId` |
| `useRfi(rfiId)` | `["rfi", rfiId]`, `enabled: !!rfiId` |
| `useRfiProposals(projectId)` | `["rfi-proposals", projectId]` |
| `useCreateRfi(projectId)` | invalidate `["rfis", projectId]`, `["rfi-proposals", projectId]` |
| `useUpdateRfi(projectId)` | invalidate `["rfis", projectId]` и `["rfi", rfiId]` |
| `useDeleteRfi(projectId)` | invalidate `["rfis", projectId]`, `["rfi-proposals", projectId]` |
| `useEscalateRfi(projectId)` | invalidate `["rfis", projectId]`, `["rfi-proposals", projectId]` |
| `useCreateRfiFromProposal(projectId)` | invalidate `["rfis", projectId]`, `["rfi-proposals", projectId]` |

`useUpdateRfi` принимает `projectId` именно для инвалидации списка —
в `useDecisions` этого нет (там список после edit не обновляется), повторять
этот дефект не нужно.

`useRfi` экспортируется, потому что спека требует 8 хуков, но в `RfiPage`
**не импортируется** (нет потребителя — иначе `noUnusedLocals` уронит
сборку). Данные для edit берутся из уже загруженного списка `useRfis`.

### 5.3 `RfiCard.tsx`

Props:
```ts
{
  rfi: Rfi
  causeLabel: string | null
  premiseLabels: string[]   // полный список; карточка показывает 3 + «+N»
  onEdit: (rfi: Rfi) => void
  onDelete: (rfiId: string) => void
}
```

Содержимое:
- `Card` + `CardHeader`: `title` (line-clamp), `Badge` цвета
  `RFI_STATE_COLORS[rfi.rfi_state]` с текстом `RFI_STATE_LABELS[...]`.
- `CardContent`:
  - «Причина:» `causeLabel` или «—»;
  - «Срок:» `rfi_due_date` в `toLocaleDateString("ru-RU")`, при просрочке —
    `text-red-600 font-medium` + подпись «просрочен»;
  - «Связи:» `premiseLabels.slice(0, 3)` как `Badge variant="secondary"`;
    при `premiseLabels.length === 0` — «—», при > 3 — бейдж «+N»,
    где N = `premiseLabels.length - 3`;
  - `created_at` мелким шрифтом.
- `CardFooter`: «Изменить» (outline, `Pencil`), «Удалить» (destructive, `Trash2`).
- Просрочка: `rfi.rfi_due_date !== null && rfi.rfi_due_date < todayISO &&
  !["closed", "registered"].includes(rfi.rfi_state)`, где `todayISO` —
  локальная дата `YYYY-MM-DD` (строковое сравнение ISO-дат, без TZ-сдвигов).
- `closed`/`registered` карточку не скрывают.

Кнопки эскалации в карточке **нет** — она в списке предложений (спека §9).

### 5.4 `RfiForm.tsx`

Props:
```ts
{
  initialData?: Rfi | null
  causeOptions: {
    decisions: { id: string; label: string }[]
    goals: { id: string; label: string }[]
  }
  onSubmit: (payload: RfiCreate) => void
  onCancel: () => void
  submitting?: boolean
}
```

Поля:
1. «Заголовок» — `Input`, обязателен, `maxLength={1000}`
   (иначе backend вернёт 422); submit disabled при `!title.trim()`.
2. «Тип причины» — `Select` (`decision` | `goal`). При редактировании
   **заблокирован**, если у RFI уже есть причина (`rfi_cause_* != null`);
   если причина отсутствует — выбор доступен.
3. «Причина» — `Select` из `causeOptions.decisions` или `.goals`
   (пустой список → подсказка «Нет доступных решений/целей», submit disabled).
4. «Срок RFI» — `Input type="date"`.
   - create: необязателен;
   - edit: обязателен, **если** `initialData.rfi_due_date !== null`
     (очистка невозможна из-за `None`-sentinel; подсказка «Срок можно
     изменить, но не очистить»). Если срок не был задан — поле можно
     оставить пустым, тогда оно не отправляется.
5. «Состояние» — `Select` по всем 6 значениям `RFI_STATE_LABELS`.

Правила сабмита:
- Отправляется **только** выбранная сторона причины; вторая в payload
  не попадает. Без причины отправка запрещена: backend вернёт `400`
  по XOR-правилу.
- При редактировании тип причины не меняется; срок непустой, только если был задан изначально.
- Пустой `rfi_due_date` при create → поле не отправляется.
- Паттерн состояния — `useState` + `useEffect` от `initialData`
  (как `DecisionForm.tsx`); React Hook Form / Zod не используем.
- Ошибка сервера показывается на странице (`Alert`), не внутри формы.

### 5.5 `RfiProposalList.tsx`

Props:
```ts
{
  proposals: RfiProposal[]
  onCreateFromProposal: (p: RfiProposal) => void
  onEscalate: (p: RfiProposal) => void
  onRefresh: () => void
  approving: boolean
}
```

- Заголовок «Предложенные RFI» + счётчик + кнопка «Обновить» (`RefreshCw`).
- Пусто → «Предложений нет».
- `Badge` правила: `decision_без_ид` → «Решение без ИД»,
  `rfi_просрочен` → «RFI просрочен», иначе — сырое `rule`.
- Формулировка, `rationale` (если есть), `rfi_due_date`.
- Ключ элемента — общий helper `proposalKey(p)`: объявить его рядом с типом
  `RfiProposal` в `rfiApi.ts` и использовать в `RfiProposalList` и на
  странице: `` `${p.id ?? "no-id"}:${p.reason_decision_id ?? p.existing_rfi_id ?? ""}` ``.
  Причина: `id` nullable, а детерминированный `uuid5` строится из
  `rule:formulation:existing_rfi_id` без `reason_decision_id` — у двух
  Decision с одинаковой формулировкой `id` совпадёт, поэтому одного `id`
  для ключа недостаточно.
- `action="create"` → кнопка «Создать». `disabled`, если нет
  `reason_decision_id` или `rfi_due_date` (иначе backend даст 422).
  Клик → `onCreateFromProposal(p)`; маппинг в payload делает страница.
- `action="escalate"` → кнопка «Эскалировать». `disabled`, если нет
  `existing_rfi_id`. Клик → `onEscalate(p)`; страница вызывает
  `escalateRfi(p.existing_rfi_id)`.
- `approving` дизейблит все кнопки блока.
- Компонент не знает про API и не строит payload — только события.

### 5.6 `RfiPage.tsx`

Каркас копирует `DecisionsPage.tsx`:

1. `useParams<{ id: string }>()` → `projectId`; при отсутствии — заглушка.
2. Запросы: `useRfis(projectId)`, `useRfiProposals(projectId)`,
   `useDecisions(projectId)`, `useGoals(projectId)`,
   `usePremises(projectId)` (для подписей связей), проект — тем же способом,
   что в `DecisionsPage`.
3. Мутации: create/update/delete/escalate/from-proposal.
4. Карты подписей на странице:
   - `causeLabel`: из decisions и goals (`formulation` — подтверждено
     в `api/decisionApi.ts`, `api/goalApi.ts`);
   - `premiseLabels`: по `premise_ids` из `api/premiseApi.ts`, поле подписи —
     `name` (подтверждено); передаётся полный список.
5. Маппинг предложения в `RfiProposalApprove` — на странице:
   `{ formulation, rationale, rfi_cause_decision_id: reason_decision_id,
      rfi_due_date, rfi_state: "open" }`.
6. **Локальное скрытие обработанных предложений:** `useState<Set<string>>`
   (`handledProposals`) — после успешного `from-proposal`/`escalate`
   в набор кладётся `proposalKey(p)` (см. §5.5); список фильтруется. Кнопка
   «Обновить» очищает набор (сервер не дедуплицирует предложения).
7. Ошибка любой мутации → `Alert variant="destructive"` с текстом операции
   («Не удалось создать RFI» и т.п.). `onError` задаётся **для каждой**
   мутации, включая delete (в `DecisionsPage` delete без `onError` —
   не копировать). Текст `detail` не извлекаем: `apiClient` его не
   нормализует (изменение общего клиента вне задачи).
8. Заголовок: `ArrowLeft` → `/projects/{id}`, «RFI{ — project.name}»,
   подзаголовок «Запросы информации по проекту», кнопка «Добавить RFI».
9. Порядок: предложения → список.
10. Empty state «Пока нет RFI» + кнопка «Добавить RFI».
11. Список — grid `grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-4`.
12. Создание/редактирование — `Dialog` + `RfiForm`, `initialData` — элемент
    из `rfis`; при закрытии сброс `showForm`/`editingId`.
    Удаление — `window.confirm` (как в `DecisionsPage`; `ConfirmDialog`
    из `canvas/` не переиспользуем, чтобы не менять соглашение страниц).
13. Никаких фильтров/поиска/сортировки: вне 6.12d.

## 6. Поведение и UX-правила

| Ситуация | Поведение |
|---|---|
| Загрузка списка/предложений | «Загрузка...» |
| Ошибка загрузки | `Alert variant="destructive"` «Ошибка загрузки RFI» |
| Пустой список | «Пока нет RFI» + кнопка «Добавить RFI» |
| Нет предложений | «Предложений нет» |
| Просрочка | срок красным + «просрочен» |
| `escalated` | бейдж красный, карточка остаётся в списке |
| `closed` / `registered` | карточка остаётся, edit/delete доступны |
| Двойной клик по «Создать» | кнопки блока дизейблятся на время мутации |
| Обе причины сразу | невозможно: один зависимый `Select` |

## 12. Риски и митигации

| Риск | Митигация |
|---|---|
| Случайно застейджить чужой техдолг | Только явные пути в `git add`; проверка `git diff --cached --name-only` |

| 400 вместо 404 при delete/escalate | Общий `Alert`, без ветвления по 404 |
| `from-proposal` 422 при неполном предложении | Кнопка дизейблится при отсутствии `reason_decision_id`/`rfi_due_date` |
| TZ-сдвиг при сравнении дат | Сравнение ISO-строк `YYYY-MM-DD` с локальной `todayISO` |
