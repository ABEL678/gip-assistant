# AUDIT_PROMPTS.md — промпты для GLM-5.3 (аудитор)

> **Назначение:** шаблоны промптов для независимого аудита через GLM-5.3
> (GigaCode Ask mode). Пишет координатор (DeepSeek), копирует человек
> в GigaCode Ask. GLM не меняет код — только отчёт.
>
> **Когда использовать:** см. §«Три точки встраивания» в HANDOFF.md.

---

## 1. Аудит плана (перед кодом)

**Когда:** перед каждым промптом на реализацию (6.12a–e). Дёшево.

**Промпт для GLM-5.3:**

```
Роль: независимый аудитор плана. Не меняй файлы. Только найди проблемы.

Контекст: «ГИП-Ассистент», FastAPI + SQLAlchemy 2.0 async + PostgreSQL 15.
Гексагональная архитектура. Домен чистый.

Задача: проверь план <сессия> (`<путь к плану>`) против спеки
`docs/specs/spec_week_4.md` <§>.

Проверь:
1. Противоречия между планом и спекой (поля, индексы, CHECK, порядок шагов).
2. Пропущенные поля/индексы/CHECK, которые спека требует, а план — нет.
3. Порядок шагов: что должно быть до чего (enum → модель → миграция → DTO → репо → тесты).
4. Риски миграции: downgrade, drop enum, порядок drop.
5. Паттерны проекта: enum-маппинг, save через merge, _to_domain/_to_model.

Формат: список проблем (файл:строка / проблема / серьёзность: блокер|важно|косметика / как исправить).
Если проблем нет — «Проблем не найдено. Проверено: …».
```

## 2. Аудит кода (после реализации, до коммита)

**Когда:** после реализации, до коммита. Средне.

**Промпт для GLM-5.3:**

```
Роль: независимый аудитор кода. Не меняй файлы. Только найди проблемы.

Контекст: «ГИП-Ассистент», FastAPI + SQLAlchemy 2.0 async + PostgreSQL 15.
Гексагональная архитектура. Домен чистый (без FastAPI/SQLAlchemy/Pydantic).

Задача: проверь изменения в рабочем дереве (`git diff HEAD`) для сессии <сессия>.
Спека — `docs/specs/spec_week_4.md` <§>.

Проверь:
1. Соответствие спеке <§>: поля, типы, FK ondelete, CHECK, индексы.
2. CHECK-ограничения: синтаксис PostgreSQL, NULL-семантика (is_rfi NOT NULL?),
   покрытие сценариев (is_rfi=true → причина; is_rfi=false → NULL).
3. Partial-индексы: `postgresql_where=text("is_rfi = true")` — правильный синтаксис.
4. Маппинг enum в репозитории: соответствует ли паттерну `PremiseRepository`
   (`_to_domain` → `Enum(model.field)`, `_to_model` → `domain.field.value`)?
   Нет двойной обёртки?
5. DTO: `RfiCreate` без `project_id`; `RfiRead.status: TaskStatus` (не `state`);
   `premise_ids` — `default_factory=list`, не `None`. `sort_order`/`source` — есть в домене?
6. Миграция: enum создаётся явно (по паттерну `c52a3c176d47`), downgrade работает,
   порядок drop правильный.
7. Тесты: не проходят «случайно» (assert на None без проверки полей)?
   Покрывают ли CHECK-сценарии?

Формат: список проблем (файл:строка / проблема / серьёзность: блокер|важно|косметика / как исправить).
Если проблем нет — «Проблем не найдено. Проверено: …».
```

## 3. Архитектурный аудит (раз в веху)

**Когда:** раз в веху. Дорого.

**Промпт для GLM-5.3:**

```
Роль: независимый архитектурный аудитор. Не меняй файлы. Только найди проблемы.

Контекст: «ГИП-Ассистент». Гексагональная архитектура (domain / application / adapters).
Домен чистый. Спека — `docs/specs/spec_week_4.md`.

Задача: архитектурный аудит после закрытия вехи 4 (6.12a–e).
Контекст — `backend/src/domain/`, `backend/src/adapters/db/repositories/`.

Проверь:
1. `Task.is_rfi` vs отдельная таблица `rfis` — есть ли скрытые проблемы
   (дублирование TaskRepository, расхождение Task.state и rfi_state).
2. Связь RFI → Document → Premise — не теряется ли источник (откуда пришёл ИД).
3. `RfiRepository` (6.12b) — не дублирует ли `TaskRepository`? Достаточно ли
   специализации (list_rfis_by_project и т.п.)?
4. `RfiProposalService` — правила не противоречат `DecisionProposalService`?
5. Циклические зависимости, дублирование, нарушения слоёв.

Формат: 3–5 пунктов, только существенное. Файл:строка / проблема / серьёзность / как исправить.
```
