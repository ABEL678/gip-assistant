## 1. Общие сведения

### 1.1. Назначение продукта

ГИП-Ассистент — облачная (SaaS) система управления проектной разработкой для микро-студий и проектных институтов.

**Что решает:**

1. Координация смежников — 10/12 интервьюированных назвали главной болью.
2. Контроль просрочек — 9/12.
3. Потеря задач — 8/12.
4. Согласования — 7/12 (MVP-2).
5. Изменения / РВИ — 6/12 (MVP-2).

**Ключевые новшества 6.3 / 4.3:**

- Универсальные сущности — ГИП сам создаёт свои типы (ИД, Запросы, Протоколы) под свои привычки.
- Формирование электронной ПД в XML-формате — обязательное требование Минстроя и Главгосэкспертизы.
- AI-контекст — единая система для работы с ИИ-ассистентами и будущими разработчиками.
- GigaCode + самописный ИИ-агент — инструменты разработки в российском контуре.

### 1.2. Ключевой принцип

**Минимизация ручного ввода.** Система:

- Импортирует Excel ГИПа без переделки
- Автоматически подсказывает маппинг колонок
- Формирует матрицу смежников
- Отправляет ежедневную Telegram-сводку
- Формирует XML-документы для экспертизы из уже имеющихся данных

### 1.3. Value Proposition

**Для директора (через ГИПа):**

> ГИП-Ассистент — единая среда, в которой ГИП ведёт все свои проекты: запросы Заказчику, задачи смежникам, тома, согласования, документы. Директор видит, где горят сроки, без совещаний. Документы формируются в XML и готовы к отправке в экспертизу.

### 1.4. Границы MVP

**Входит в MVP (Этап 2 — 6 недель):**

1. Универсальные сущности (EntityType + Entity)
   - CRUD API
   - UI конструктора типов
   - Импорт Excel в generic
   - Универсальная таблица с фильтрами

2. Библиотека шаблонов (6 типов)
   - ИД_ПД, ИД_РД
   - Запросы
   - Тома
   - Письма
   - Протоколы

3. Документы (MinIO AIStor Free)
   - Загрузка / скачивание / удаление
   - Прикрепление к проекту и сущностям
   - Метаданные в PostgreSQL

4. Аутентификация
   - JWT + Argon2
   - Регистрация / логин
   - Изоляция данных по user_id
   - Роли: ГИП / Дизайнер / Наблюдатель

5. Telegram-сводка
   - Cron 09:00

6. Деплой на VPS
   - Docker Compose
   - Nginx + SSL

7. Лендинг (Next.js)

8. Комплаенс 152-ФЗ

### 1.5. Архитектурные запреты

**Строго НЕ используем в MVP:**

- Celery, Redis, RabbitMQ
- Webhooks
- Парсинг API Vitro-CAD (только CSV)
- Публичное облако для LLM (только локально)
- Облачные аналитические скрипты (Google Analytics, Yandex Metrica на стороне клиента)
- MinIO Community Edition (архивирован)
- Claude Code (недоступен без VPN, риск блокировки)
- Cursor Composer (требует иностранных карт, менее безопасен)

**Разрешено в MVP:**

- Синхронные запросы
- BackgroundTasks FastAPI + отдельный воркер
- cron внутри Docker-контейнера
- Ручной триггер интеграций
- Docker Compose с первого дня
- MinIO AIStor Free
- Qwen 2.5 7B локально (MVP-3)
- GigaCode в PyCharm — для разработки (автодополнение, простые задачи)
- Самописный ИИ-агент на GigaChat API — для автономных задач (в MVP, Неделя 1-2)
- `gpt2giga` — как опция (если понадобится OpenAI-совместимый интерфейс)

## 3. Архитектура

### 3.1. Паттерн: порты и адаптеры (гексагональная архитектура)

**Backend:** домен (`backend/src/domain/`) не зависит от FastAPI, SQLAlchemy, HTTP. Все взаимодействия — через порты.

**Frontend:** React-компоненты не знают о структуре API. Все данные — через API-клиент (`frontend/src/api/`).

**Website:** Next.js не зависит от backend. Только форма заявки и статический контент.

### 3.2. Слои Backend

| Слой | Содержание | Зависимости |
|------|-----------|-------------|
| Domain | Сущности, VO, порты, доменные сервисы | Только stdlib + typing |
| Models (адаптер БД) | SQLAlchemy-модели | SQLAlchemy, Domain |
| Repositories | Реализация портов | Models, Domain |
| API (адаптер HTTP) | FastAPI-роуты, Pydantic-схемы | FastAPI, Domain, Repositories |
| Application | Оркестрация use cases | Domain, Repositories |
| Storage (адаптер S3) | MinIO AIStor | aioboto3, Domain |
| XML (адаптер) | lxml + xmlschema | lxml, xmlschema, Domain |
| Worker | Отдельный процесс для парсинга | Domain, Repositories |
| LLM (адаптер) | Qwen 2.5 | llama-cpp-python, Domain |


### 3.3. Гибридная модель данных

**Системные сущности (фиксированные):**

- `Project`, `Task`, `CrossTask`, `ImportLog`, `User`, `Executor`
- `Document`, `DocumentVersion`, `DocumentLink`, `DocumentType` (новое в 4.4)
- `XMLSchema`, `XMLDocument` (новое в 4.2)
- **Участвуют в системных фичах:** матрица смежников, Telegram-сводка, импорт, XML-экспорт, ГОСТ-хранение

**Пользовательские сущности (generic):**

- `EntityType` — тип («Исходные данные»)
- `Entity` — экземпляр («ТУ на водоснабжение»)
- **Хранятся в JSONB**, схема — динамическая
- **Расширение:** `EntityType.xml_schema_code` — связь с XSD Минстроя

### 3.7. XML-формат и схемы Минстроя (новое в 4.2)

**Обязательные документы:**

1. **ТЗ** (Задание на проектирование) — обязательно с июля 2025
2. **ПЗ** (Пояснительная записка) — обязательно с января 2026, версия 1.06

**Принципы:**

1. Схемы скачиваются с сайта Минстроя (`minstroyrf.gov.ru/tim/xml-skhemy/`)
2. Кэшируются в БД (таблица `xml_schemas`)
3. Проверяются на обновление при каждом обращении к модулю экспорта
4. Генерация XML — на основе данных `Entity.data` + маппинга на XSD
5. Валидация — обязательна до выдачи файла ГИПу
6. Ошибки валидации — показываются пользователю

**Что делаем в MVP-1.5:**

- Модель `XMLSchema` — метаданные схем
- Модель `XMLDocument` — сформированные XML
- Сервис `SchemaService` — скачивание, кэш, обновление
- Сервис `XMLService` — генерация, валидация
- UI: мастер экспорта + просмотр ошибок

**Что НЕ делаем:**

- Автоматическую отправку в ЕЦПЭ (MVP-3+)
- Все разделы ПД (только ТЗ и ПЗ)
- Редактор XML в интерфейсе

### 5.7. Функция 6 (новая): Формирование XML-документов

**Приоритет:** критический (ядро MVP-1.5).
**Срок:** Этап 2.5 (2 недели).

#### 5.7.1. Описание

ГИП формирует **ТЗ** и **ПЗ** в XML-формате для сдачи в государственную экспертизу.

**Как работает:**

1. ГИП создаёт тип сущности «Электронный документ ПД» (или использует шаблон)
2. Выбирает **схему Минстроя**: ТЗ или ПЗ
3. Заполняет поля, соответствующие элементам XML-схемы
4. Нажимает «Экспорт XML» — система:
   - Генерирует XML из данных `Entity.data`
   - Валидирует по актуальной XSD
   - Сохраняет результат в MinIO
   - Показывает ошибки валидации (если есть)
5. Скачивает готовый XML

**Схемы Минстроя:**

- Скачиваются с `minstroyrf.gov.ru/tim/xml-skhemy/`
- Кэшируются в таблице `xml_schemas`
- Проверяются на обновление при каждом обращении к модулю

### 6.10. Компонент DynamicField

```tsx
// frontend/src/components/DynamicField.tsx

export function DynamicField({ field, value, onChange, readOnly }: DynamicFieldProps) {
  switch (field.type) {
    case "text":
      return <Input value={value || ""} onChange={(e) => onChange(e.target.value)} disabled={readOnly} />
    case "textarea":
      return <Textarea value={value || ""} onChange={(e) => onChange(e.target.value)} disabled={readOnly} />
    case "number":
      return <Input type="number" value={value ?? ""} onChange={(e) => onChange(Number(e.target.value))} disabled={readOnly} />
    case "date":
      return <Input type="date" value={value || ""} onChange={(e) => onChange(e.target.value)} disabled={readOnly} />
    case "boolean":
      return <Checkbox checked={!!value} onCheckedChange={onChange} disabled={readOnly} />
    case "select":
      return (
        <Select value={value || ""} onValueChange={onChange} disabled={readOnly}>
          <SelectTrigger><SelectValue /></SelectTrigger>
          <SelectContent>
            {field.options?.map((opt) => (
              <SelectItem key={opt} value={opt}>{opt}</SelectItem>
            ))}
          </SelectContent>
        </Select>
      )
    case "multiselect":
      return <MultiSelect options={field.options || []} value={value || []} onChange={onChange} disabled={readOnly} />
    case "url":
      return <Input type="url" value={value || ""} onChange={(e) => onChange(e.target.value)} disabled={readOnly} />
    case "email":
      return <Input type="email" value={value || ""} onChange={(e) => onChange(e.target.value)} disabled={readOnly} />
    default:
      return <span className="text-muted-foreground">Неизвестный тип: {field.type}</span>
  }
}
```

```tsx
  const navigate = useNavigate()

  useEffect(() => {
    if (!isLoading && !user) {
      navigate("/login")
    }

  if (!user) return null

  return <>{children}</>
```

## 8. LLM-ассистент (MVP-3)

### 8.1. Обзор

**Не входит в MVP.** Раздел — для планирования MVP-3.

**Цель:** локальный ИИ-ассистент:

- RAG по документам проекта
- Генерация писем, отчётов, ТЗ
- Извлечение задач из протоколов
- Ответы на вопросы по проекту

### 8.2. Модель Qwen 2.5 7B

**Почему Qwen 2.5:**

- Русский язык — отличный
- Open-source — Apache 2.0
- Локально — данные не уходят
- 7B параметров — влезает в 16 GB RAM (quantized)
- Контекст 32K — достаточно для документов

**Варианты:**

| Вариант | RAM | Скорость | Качество |
|---------|-----|----------|----------|
| Qwen 2.5 7B (Q4_K_M) | ~6 GB | среднее | хорошее |
| Qwen 2.5 7B (Q5_K_M) | ~7 GB | среднее | очень хорошее |
| Qwen 2.5 14B (Q4) | ~10 GB | медленное | отличное |

**Для VPS 16 GB RAM:** Qwen 2.5 7B (Q5_K_M).

### 8.4. RAG — Retrieval-Augmented Generation

**Пайплайн:**

1. Загрузка документа → парсинг (PDF, DOCX) → чанки по 500 токенов
2. Эмбеддинги через `nomic-embed-text`
3. Сохранение в pgvector с метаданными
4. Запрос пользователя → эмбеддинг → поиск top-5 чанков
5. Контекст + запрос → LLM → ответ
6. Цитирование источников

### 8.5. Сценарии MVP-3

**Сценарий 1. Генерация письма**

```
ГИП: "Напиши письмо Заказчику о переносе сроков по АР"
LLM:
  - Находит шаблоны писем в проекте
  - Извлекает контекст (задачи АР, сроки, причины)
  - Генерирует черновик
ГИП: правит → отправляет
```

**Сценарий 2. Извлечение задач из протокола**

```
ГИП загружает протокол совещания (DOCX)
LLM:
  - Извлекает поручения
  - Определяет ответственных и сроки
  - Предлагает список задач
ГИП: подтверждает → задачи создаются
```

**Сценарий 3. Вопрос по проекту**

```
ГИП: "Что мы решили по вентиляции на последнем совещании?"
LLM: ищет в протоколах, находит, отвечает с цитатами
```

### 8.6. Технические требования

**VPS для LLM:**

| Параметр | Минимум |
|----------|---------|
| RAM | 16 GB |
| CPU | 8 vCPU |
| Диск | 80 GB SSD |
| GPU | опционально (ускоряет x5-x10) |

**Стоимость:** ~1500-2000 ₽/мес (Timeweb, Selectel, Aeza).

**Модели (GGUF):**

- `qwen2.5-7b-instruct-q5_k_m.gguf` (~5.5 GB)
- `nomic-embed-text-v1.5.Q5_K_M.gguf` (~130 MB)

**Размещение:** `/models/` на VPS (вне репозитория, в `.gitignore`).

### 8.7. Что НЕ делаем в MVP-3

- Fine-tuning модели
- Мультимодальность (изображения)
- Голосовой ввод
- Агентные сценарии (LLM сам делает действия)
- Облачные LLM (только локально)

### 8.8. Метрики качества

- Точность извлечения задач: > 80%
- Приемлемость черновиков писем: > 70%
- Время ответа: < 10 секунд
- Галлюцинации: < 5% (проверка фактов по RAG)

```nginx
        }
```

### 15.8. Почему НЕ Claude Code и НЕ Cursor

**Claude Code:**

- Anthropic официально не поддерживает РФ.
- С 2026 — массовые блокировки российских аккаунтов.
- Оплата требует иностранной карты.
- Потеря аккаунта = потеря всего рабочего контекста.

**Cursor:**

- Требует оплаты через иностранные карты.
- Менее прозрачен в отношении российских пользователей.
- Дороже, чем GigaCode.

**Решение:** только инструменты с официальной поддержкой в РФ.

### 16.5. Сервисы

#### 16.5.1. DocumentService

```python
# backend/src/domain/services/document_service.py

from uuid import UUID, uuid4
from datetime import datetime, timezone
from hashlib import sha256

from backend.src.domain.entities.document import Document, DocumentVersion, DocumentLink
from backend.src.domain.ports.document_repository import DocumentRepository
from backend.src.domain.ports.storage_port import StoragePort
from backend.src.domain.value_objects.document import (
    DocumentKind, DocPartType, LifecycleStatus, DocumentLinkType,
)


class DocumentService:
    """Сервис управления документами (ГОСТ Р 21.101-2026)."""

    def __init__(
        self,
        document_repo: DocumentRepository,
        storage: StoragePort,
    ):
        self._repo = document_repo
        self._storage = storage

    # --- Документы ---

    async def create_document(
        self,
        project_id: UUID,
        cipher: str,
        document_name: str,
        document_type_id: UUID,
        document_kind: DocumentKind,
        doc_part_type: DocPartType | None = None,
        section_code: str | None = None,
        mark: str | None = None,
        base_designation: str | None = None,
        entity_id: UUID | None = None,
        task_id: UUID | None = None,
        created_by: UUID | None = None,
    ) -> Document:
        """Создать карточку документа.

        GUID генерируется в приложении (UUIDv4), не в БД.
        GUID не меняется при выпуске новых версий (ГОСТ 8.2.4).
        """
        document = Document(
            id=uuid4(),
            guid=uuid4(),  # постоянный идентификатор
            project_id=project_id,
            entity_id=entity_id,
            task_id=task_id,
            cipher=cipher,
            base_designation=base_designation,
            section_code=section_code,
            document_kind=document_kind,
            mark=mark,
            doc_part_type=doc_part_type,
            document_name=document_name,
            document_type_id=document_type_id,
            lifecycle_status=LifecycleStatus.DRAFT,
            created_by=created_by,
            created_at=datetime.now(timezone.utc),
            updated_at=datetime.now(timezone.utc),
        )
        return await self._repo.create(document)

    async def get_document(self, document_id: UUID) -> Document | None:
        return await self._repo.get(document_id)

    async def list_documents(self, project_id: UUID) -> list[Document]:
        return await self._repo.list_by_project(project_id)

    async def update_document(
        self,
        document_id: UUID,
        **fields,
    ) -> Document | None:
        document = await self._repo.get(document_id)
        if document is None:
            return None
        for key, value in fields.items():
            if value is not None and hasattr(document, key):
                setattr(document, key, value)
        document.updated_at = datetime.now(timezone.utc)
        return await self._repo.update(document)

    async def delete_document(self, document_id: UUID) -> bool:
        """Удалить документ. Версии удаляются каскадно (ON DELETE CASCADE)."""
        return await self._repo.delete(document_id)

    # --- Версии ---

    async def create_version(
        self,
        document_id: UUID,
        version: str,
        file_data: bytes,
        file_name: str,
        format_original: str,
        format_archive: str | None = None,
        change_number: int | None = None,
        uploaded_by: UUID | None = None,
    ) -> DocumentVersion:
        """Создать версию файла.

        1. Считаем hash_sha256.
        2. Загружаем в MinIO.
        3. Снимаем флаг is_current со старой версии.
        4. Ставим флаг is_current на новую.
        5. Обновляем current_version_id у документа.
        """
        document = await self._repo.get(document_id)
        if document is None:
            raise ValueError(f"Document {document_id} not found")

        hash_sha256 = sha256(file_data).hexdigest()

        # Загрузка в MinIO
        storage_key = (
            f"projects/{document.project_id}/documents/"
            f"{document_id}/{version}_{file_name}"
        )
        await self._storage.upload(
            key=storage_key,
            data=file_data,
            content_type=format_original,
        )

        # Снять флаг is_current со старой версии
        await self._repo.unset_current_version(document_id)

        # Создать новую версию
        doc_version = DocumentVersion(
            id=uuid4(),
            document_id=document_id,
            version=version,
            change_number=change_number,
            file_path=storage_key,
            file_name=file_name,
            hash_sha256=hash_sha256,
            format_original=format_original,
            format_archive=format_archive,
            size_bytes=len(file_data),
            is_current=True,
            uploaded_by=uploaded_by,
            uploaded_at=datetime.now(timezone.utc),
        )
        created = await self._repo.create_version(doc_version)

        # Обновить current_version_id у документа
        await self._repo.update_current_version(document_id, created.id)

        return created

    async def list_versions(self, document_id: UUID) -> list[DocumentVersion]:
        return await self._repo.list_versions(document_id)

    async def get_current_version(
        self, document_id: UUID
    ) -> DocumentVersion | None:
        return await self._repo.get_current_version(document_id)

    async def delete_version(self, version_id: UUID) -> bool:
        """Удалить версию. Если удаляем текущую — надо назначить новую."""
        version = await self._repo.get_version(version_id)
        if version is None:
            return False

        was_current = version.is_current
        await self._storage.delete(version.file_path)
        deleted = await self._repo.delete_version(version_id)

        if deleted and was_current:
            remaining = await self._repo.list_versions(version.document_id)
            if remaining:
                new_current = max(remaining, key=lambda v: v.uploaded_at)
                await self._repo.set_current_version(new_current.id)
                await self._repo.update_current_version(
                    version.document_id, new_current.id
                )

        return deleted

    # --- Связи ---

    async def create_link(
        self,
        source_document_id: UUID,
        target_document_id: UUID,
        link_type: DocumentLinkType,
    ) -> DocumentLink:
        link = DocumentLink(
            id=uuid4(),
            source_document_id=source_document_id,
```

### 16.6. Схема хранения в MinIO
`
gip-assistant-documents/
├── projects/
│   └── {project_id}/
│       ├── documents/
│       │   └── {document_id}/
│       │       ├── v1.0_{filename}
│       │       ├── v1.1_{filename}
│       │       └── v2.0_{filename}
│       ├── entities/
│       │   └── {entity_id}/
│       │       └── {document_id}_{filename}
│       ├── tasks/
│       │   └── {task_id}/
│       │       └── {document_id}_{filename}
│       ├── xml/
│       │   └── {xml_document_id}_{schema_code}.xml
│       └── common/
│           └── {document_id}_{filename}
`
Правило:

Новые документы (Уровень 1.5+) → documents/{document_id}/{version}_{filename}.

Каждая версия — отдельный файл. Старые версии не удаляются при выпуске новой.

Старые документы (загруженные до Уровня 1.5) остаются в entities/, tasks/, common/ — не трогаем.
