## Что нового в 7.0

- Два столпа онтологии: (1) вводные + логика + механизм вывода = структура; (2) система знает вводные → предлагает структуру → ГИП утверждает.
- Формула ядра: трёхэлементная (вводные + логика + механизм вывода).
- Механизм вывода двухуровневый: правила (вехи 1–5) + LLM (веха 6).
- 6 вех × 4 недели = 24 недели (20 недель продукт + 4 недели пилот).
- Агенты — не MVP-3, а раньше. XML — часть агента XML, не отдельная веха.
- MinIO — инструмент для документов, не веха.
- DOMAIN.md v1.1 — главный документ онтологии.

## §2. Принципы 7.0

### 2.1. Из DOMAIN.md v1.1

1. **Вводные + логика + механизм вывода = структура управления проектом.** Без механизма вывода — таск-трекер. С механизмом — соавтор.
2. **Система знает вводные → предлагает структуру → ГИП утверждает.** Это не таск-трекер. ГИП — редактор, не «кнопка ок».
3. **Механизм вывода двухуровневый.** Правила (вехи 1–5) — простые предложения. LLM (веха 6) — сложные.
4. **ГИП — редактор.** Утверждает, правит, отклоняет, утверждает списком.
5. **Осторожность предложений.** Вехи 1–5 — только явное из вводных. Веха 6 — адаптивно.
6. **Агент предлагает — ГИП решает.** Автономия — только там, где делегировано.
7. **Агенты — сотрудники с ролью.** Не фоновые процессы. Имя, роль, зона ответственности.

### 2.2. Принципы карты

1. **Веха = 4 недели = видимый результат для ГИПа.**
2. **Ценность раньше полноты.** ГИП получает пользу с первой вехи.
3. **Адаптируем, не переписываем.** Используем то, что уже сделано (6.4).
4. **Открытые вопросы решаются внутри вех.** Не откладываем на потом.
5. **Демо в конце каждой вехи.** ГИП видит результат.

### 2.3. Из 6.4 (живут)

- Домен чистый (без FastAPI/SQLAlchemy).
- Порты и адаптеры (гексагональная архитектура).
- Гибридная модель данных (системные + generic).
- ГОСТ-совместимость — фундамент.
- XML — обязательность.
- AI-контекст — часть продукта.
- Только российские ИИ-инструменты (GigaCode).
- GUID документа.
- DocumentVersion + DocumentLink.

## §3. Ценность для ГИПа

### 3.1. Топ-5 болей (из 12 интервью)

| Боль | Частота | Покрытие вехами |
|------|---------|-----------------|
| Координация смежников | 10/12 | Веха 1 (вводные), веха 2 (Action) |
| Контроль просрочек | 9/12 | Веха 5 (агент сроков) |
| Потеря задач | 8/12 | Веха 1 (Goal), веха 2 (Action) |
| Согласования | 7/12 | После пилота (§7) |
| Изменения / РВИ | 6/12 | После пилота (§7) |

### 3.2. Что закрывает продукт после вехи 5

**3 из 5 болей:**

1. **Координация смежников.** Вводные как сущности + Goal → Decision → Task → Action. ГИП видит полную картину связей.
2. **Контроль просрочек.** Агент сроков (веха 5) — напоминания, эскалация, Telegram-сводка.
3. **Потеря задач.** Action как атомарная единица с измеримым результатом. Система предлагает из вводных.

**Согласования и РВИ — после пилота** (§7).

## §4. Обзор вех

| # | Веха | Недель | Что даёт ГИПу | Ключевые артефакты |
|---|------|--------|---------------|-------------------|
| 1 | Система знает вводные и предлагает цели | 4 | Видит договор/ТЗ/ИД как сущности. Утверждает цели из вводных. | Вводные, Goal, механизм вывода на правилах |
| 2 | Система предлагает действия | 4 | Видит каждое действие с измеримым результатом. Task адаптирован. | Action, Task-адаптация, связи с Decision |
| 3 | Система предлагает решения и связи | 4 | Видит решения, обоснования, связи Goal ↔ Decision ↔ Task. | Decision, Norm, DecisionLink, связи |
| 4 | Система ведёт RFI | 4 | Не теряет запросы на данные. RFI → новые ИД → пополнение вводных. | RFI, Document ↔ Action, живые вводные |
| 5 | Система следит за сроками | 4 | Видит дашборд сроков. Получает напоминания в Telegram. | Агент сроков, Telegram-бот, настройки |
| 6 | Пилот | 4 | LLM, XML, Auth, деплой. Первый платящий клиент. | Лендинг, комплаенс, пилот 7 дней |

**Продукт (вехи 1–5):** 20 недель. **Пилот (веха 6):** 4 недели. **Итого:** 24 недели.

## §5. Детализация вех 1–5 (продукт)

### Веха 1: Система знает вводные и предлагает цели (4 недели)

**Ценность.** ГИП видит договор, ТЗ, требования Заказчика, ИД, нормы, НПА — не как файлы, а как сущности с атрибутами. Система предлагает Goal на основе вводных. ГИП утверждает.

#### 5.1.1. Что входит

**Домен + модель + миграция:**
- Вводные как сущности: `Premise` (вводная предпосылка). Каждая категория — отдельная сущность (Договор, ТЗ, Требования, ИД, Нормы, НПА, Гос.бюрократия, Внутренние ресурсы) или одна обёртка `Premise` с полем `category` — вопрос 1.
- Goal: формулировка, срок, ответственный, приоритет, состояние (план / в работе / достигнуто / отменено).
- Связи Goal → Decision (M:N).
- Связи Goal ↔ Premise (M:N).
- Миграции Alembic.

**DTO + порты + репозитории + сервисы:**
- DTO: `PremiseSchema`, `GoalSchema`, `GoalCreate`, `GoalRead`, `GoalUpdate`.
- Порты: `PremiseRepository`, `GoalRepository`.
- Репозитории: `SqlAlchemyPremiseRepository`, `SqlAlchemyGoalRepository`.
- Сервисы: `PremiseService`, `GoalService`.
- Валидации: уникальность кода, existence checks, same project.

**DI + эндпоинты:**
- DI: `get_premise_service`, `PremiseServiceDep`, `get_goal_service`, `GoalServiceDep`.
- Роуты: CRUD для Premise, CRUD для Goal, эндпоинт «предложить Goal из вводных» (правило).
- Регистрация в `main.py`.

**Тесты:**
- Unit-тесты сервисов: `test_premise_service.py`, `test_goal_service.py`.
- Smoke-тесты маппинга: `test_premise_mapping.py`, `test_goal_mapping.py`.

**UI:**
- API-клиент: `premiseApi.ts`, `goalApi.ts`.
- Хуки: `usePremises`, `useGoals`.
- Страницы: `PremisesPage`, `GoalPage`.
- Компоненты: `PremiseCard`, `GoalCard`, `GoalForm`.
- Роутинг в `App.tsx`.

#### 5.1.2. Что переиспользуем из 6.4

- Гексагональная архитектура (домен → порты → адаптеры).
- DI-инфраструктура (dependencies.py).
- DTO-паттерн (Pydantic).
- Frontend-паттерн (API-клиент → хук → страница).
- Document-модель (DocumentType, DocumentVersion, DocumentLink) — для Premise ↔ Document.

#### 5.1.3. Открытые вопросы DOMAIN.md §11

- **[Вопрос 1]** Явная сущность «Вводная»? — Открыт. Решается в вехе 1. Варианты: (A) одна обёртка `Premise` + категория как поле; (B) отдельные сущности по категориям (Договор, ТЗ, ИД, НПА, Ресурсы). Решение — после анализа сценариев.
- **[Вопрос 13]** Механизм вывода. — Веха 1: правила для Goal. Веха 2: правила для Action. Веха 3: правила для Decision. Веха 4: правила для RFI. Веха 6: LLM.
- **[Вопрос 14]** Утверждение. ГИП — редактор. Утверждает по одному, списком, с правками, отклоняет. Конкретные механики — в вехе 1.

#### 5.1.4. Выход (демо)

ГИП загружает договор → система предлагает Goal «Сдать том 7 в экспертизу» → ГИП утверждает → видит Goal в UI.

#### 5.1.5. Что НЕ входит

- Decision, Task, Action (веха 2–3).
- RFI (веха 4).
- Агент сроков (веха 5).
- LLM (веха 6).

#### 5.1.6. Риски

- Вводные — разнородные. Сложно свести к одной модели.
- Митигация: каждая категория — отдельная сущность с общим интерфейсом.

### Веха 2: Система предлагает действия (4 недели)

**Ценность.** ГИП видит каждое действие с измеримым результатом. Система предлагает Action на основе Task и вводных. Task адаптирован: связи с Decision, признак «комплексная». CrossTask как отдельная сущность убирается.

#### 5.2.1. Что входит

**Домен + модель + миграция:**
- Action: формулировка, измеримый результат, срок, ответственный, состояние (план / в работе / сделано / просрочено / отменено).
- Task: признак «комплексная» (вместо CrossTask).
- Связи: Action → Task (N:1), Task → Decision (N:1), Decision → Goal (M:N).
- Action может существовать вне Task.
- Миграции Alembic.

**DTO + порты + репозитории + сервисы:**
- DTO: `ActionSchema`, `TaskSchema` (с полем `is_complex`), `ActionCreate`, `ActionRead`, `ActionUpdate`.
- Порты: `ActionRepository`, `TaskRepository` (обновить).
- Репозитории: `SqlAlchemyActionRepository`, `SqlAlchemyTaskRepository`.
- Сервисы: `ActionService`, `TaskService` (обновить).
- Валидации: existence checks, same project, self-link.

**DI + эндпоинты:**
- DI: `get_action_service`, `ActionServiceDep`.
- Роуты: CRUD для Action, обновлённые роуты для Task.
- Эндпоинт «предложить Action из Task + вводных» (правило).

**Тесты:**
- `test_action_service.py`, `test_task_service.py` (обновить).
- Smoke-тесты маппинга.

**UI:**
- API-клиент: `actionApi.ts`.
- Хук: `useActions`.
- Страницы: `ActionPage`, обновлённый `TaskPage`.
- Компоненты: `ActionCard`, `ActionForm`, `TaskCard` (обновить).
- Роутинг.

#### 5.2.2. Что переиспользуем из 6.4

- Существующая модель Task (адаптируем).
- Document ↔ Action (связь).
- Frontend-паттерн.

#### 5.2.3. Открытые вопросы DOMAIN.md §11

### Веха 3: Система предлагает решения и связи (4 недели)

- Decision ↔ Decision: последовательные, параллельные, вложенные связи. Формализация — см. вопрос 4 (решается здесь).
- Связи: Goal ↔ Decision (M:N), Decision ↔ Task (1:N), Decision ↔ Norm (M:N).
- Миграции Alembic.

- Сервисы: `DecisionService`, `NormService`, `DecisionLinkService`.

**DI + эндпоинты:**

### Веха 4: Система ведёт RFI (4 недели)

**Ценность.** RFI как особый Task. Система не теряет запросы на данные. RFI → новые ИД → пополнение вводных. Document ↔ Action. Вводные как живые сущности.

#### 5.4.1. Что входит

**Домен + модель + миграция:**
- RFI: причина (Decision или Goal), Actions (составить запрос, отправить, получить ответ, зарегистрировать), результат (Document с новыми ИД), сроки.
- Связи: RFI → Premise (новые ИД), RFI → Document (результат).
- Миграции Alembic.

**DTO + порты + репозитории + сервисы:**
- DTO: `RfiSchema`, `RfiCreate`, `RfiRead`, `RfiUpdate`.
- Порты: `RfiRepository`.
- Репозитории: `SqlAlchemyRfiRepository`.
- Сервисы: `RfiService`.
- Валидации: existence checks, same project, причина → Decision/Goal.

**DI + эндпоинты:**
- DI: `get_rfi_service`, `RfiServiceDep`.
- Роуты: CRUD для RFI, эндпоинт «предложить RFI из Decision + вводных» (правило: для решения X нет ИД больше N дней).

**Тесты:**
- `test_rfi_service.py`.
- Smoke-тесты маппинга.

**UI:**
- API-клиент: `rfiApi.ts`.
- Хук: `useRfi`.
- Страницы: `RfiPage`.
- Компоненты: `RfiCard`, `RfiForm`.
- Роутинг.

#### 5.4.2. Что переиспользуем из 6.4

- Document-модель (DocumentVersion, DocumentLink) — для RFI → Document.
- MinIO AIStor Free — для хранения файлов RFI.
- Frontend-паттерн.

#### 5.4.3. Открытые вопросы DOMAIN.md §11

- **[Вопрос 11]** Как система видит, что ИД не хватает? — Решаем здесь: правило «для решения X нет ИД больше N дней» → RFI.

#### 5.4.4. Выход (демо)

ГИП создаёт Decision «Передать расчёт ВК» → система предлагает RFI «Нужны ИД по нагрузкам» → ГИП утверждает → RFI → Document → новые ИД пополняют вводные.

#### 5.4.5. Что НЕ входит

- Агент RFI (автоматизация, веха 5).
- Агент сроков (веха 5).
- LLM (веха 6).

#### 5.4.6. Риски

- RFI → Document → новые ИД: циклическая зависимость.
- Митигация: RFI как Task, Document как результат, Input как пополнение.

### Веха 5: Система следит за сроками (4 недели)

**Ценность.** ГИП видит дашборд сроков. Получает напоминания в Telegram. Настраивает напоминания для Goal/Task/Action/RFI. Агент сроков на правилах (без LLM).

#### 5.5.1. Что входит

**Домен + модель + миграция:**
- Настройки напоминаний: `ReminderSettings` (за N дней до срока, для сущности, для ответственного).
- Состояние напоминаний: `ReminderLog` (отправлено, просрочено).

**DTO + порты + репозитории + сервисы:**
- DTO: `ReminderSettingsSchema`, `ReminderLogSchema`.
- Порты: `ReminderSettingsRepository`, `ReminderLogRepository`.
- Репозитории: `SqlAlchemy*Repository`.
- Сервисы: `ReminderService`, `DeadlineService`.
- Агент сроков (на правилах): проверка сроков Goal/Task/Action/RFI, напоминания, эскалация.

**DI + эндпоинты:**
- DI: `get_reminder_service`, `ReminderServiceDep`, `get_deadline_service`, `DeadlineServiceDep`.
- Роуты: CRUD для ReminderSettings, эндпоинт «проверить сроки», эндпоинт «отправить напоминание».

**Worker:**
- `deadline_worker.py` — проверка сроков, отправка уведомлений.

**Telegram-бот:**
- Обновление бота: `/deadline`, `/remind`, `/status`.
- Ежедневная сводка (digest_worker).

**UI:**
- API-клиент: `deadlineApi.ts`.
- Хук: `useDeadlines`.
- Страницы: `DeadlineDashboardPage`.
- Компоненты: `DeadlineCard`, `DeadlineForm`, `ReminderSettingsForm`.
- Роутинг.

#### 5.5.2. Что переиспользуем из 6.4

- Telegram-бот (код готов, из Этапа 1).
- digest_worker (код готов, из Этапа 1).
- Document-модель.
- Frontend-паттерн.

#### 5.5.3. Открытые вопросы DOMAIN.md §11

- **[Вопрос 10]** Сколько агентов в MVP? — **Решено: один — агент сроков.** Остальные (RFI, связей, норм, XML) — после пилота.

#### 5.5.4. Выход (демо)

ГИП открывает дашборд → видит просроченные Goal/Task/Action/RFI → получает напоминание в Telegram → настраивает напоминания.

#### 5.5.5. Что НЕ входит

- LLM (веха 6).
- XML (веха 6).
- MinIO (если не в вехе 4).
- Auth (веха 6).
- Деплой (веха 6).

#### 5.5.6. Риски

- Agent сроков на правилах — без LLM, ограниченная логика.
- Митигация: правила простые, покрывают 80% случаев.

## §6. Детализация вехи 6 (Пилот, 4 недели)

**Ценность.** Первый платящий клиент. LLM (Qwen 2.5 7B) как часть механизма вывода. XML (схемы Минстроя). MinIO (если не в вехе 4). Auth (JWT + Argon2). Деплой на VPS. Лендинг. Комплаенс 152-ФЗ.

#### 6.1. LLM (Qwen 2.5 7B)

- Развёртывание на VPS (16 GB RAM, 8 vCPU).
- Подключение к агентам (механизм вывода).
- Распознавание структуры в тексте.
- Сложные предложения: «В этом письме — три решения».
- Валидация по XSD (если не в вехе 4).

#### 6.2. XML (схемы Минстроя)

- Модуль «Экспорт XML» — генерация из данных проекта.
- Модуль «Валидация XSD» — проверка перед выгрузкой.
- Сервис получения и обновления схем с сайта Минстроя.
- ТЗ и ПЗ — самые критичные.

#### 6.3. MinIO (если не в вехе 4)

- Развёртывание MinIO AIStor Free.
- Загрузка / скачивание / удаление файлов.
- Привязка к проекту, сущности, задаче.
- Presigned URLs с TTL.

#### 6.4. Auth (JWT + Argon2)

- Регистрация / логин / logout.
- Изоляция данных по user_id.
- Middleware current_user.
- Роли: ГИП / Дизайнер / Наблюдатель.

#### 6.5. Деплой на VPS

- Docker Compose на VPS.
- Nginx + SSL.
- Домен gip-assistant.ru.
- GitHub Actions CI.

#### 6.6. Лендинг

- Next.js: главная, цены, кейсы, форма заявки.
- Чекбокс 152-ФЗ.

#### 6.7. Комплаенс 152-ФЗ

- Уведомление Роскомнадзора.
- Договор-оферта (EULA).
- Политика конфиденциальности.
- Ответственный за обработку ПД.

#### 6.8. Пилот

- 7 дней бесплатно.
- Онбординг-звонок на 2-й день.
- С 8-го дня — 5 000 ₽/мес.
- Возможность отмены в первые 3 дня.
- Интервью с пилотом (1 раз в неделю).
- Первый платящий клиент.

#### 6.9. Что НЕ входит

- MVP-2 (согласования, РВИ, финансы).
- MVP-4 (интеграции).
- Мобильное приложение.
- Мультитенантность.
