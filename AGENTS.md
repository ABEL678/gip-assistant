## Ограничения

### Архитектура

- **Домен чистый.** `backend/src/domain/` **не зависит** от FastAPI, SQLAlchemy, Pydantic.
- **Порты и адаптеры.** Всё внешнее — через ABC-интерфейсы в `domain/ports/`.
- **Зависимости идут внутрь:** adapters → application → domain. Никогда наоборот.
- **Не импортируй** `fastapi`, `sqlalchemy`, `pydantic` в `domain/`.

### Backend

- **`session.commit()` вручную — нельзя.** Это делает `get_db_session` в `dependencies.py`.
- **Метод `save` в репозиториях** — через `session.merge()` (create + update).
- **Alembic — из `backend/`**, не из корня.
- **Индексы — в `__table_args__`** модели (иначе Alembic не увидит).
- **GIN для JSONB** — `Index("...", "data", postgresql_using="gin")`.
- **Enum'ы в SQLAlchemy** — использовать `Enum(EnumClass, name="...", create_type=False)`, а не `String`:
  - `Enum(PremiseCategory, name="premise_category", create_type=False)`.
  - `Enum(GoalState, name="goal_state", create_type=False)`.
  - Создаётся PostgreSQL enum-тип — валидация на уровне БД.
  - `create_type=False` — чтобы Alembic не создавал тип дважды.
  - **Проверка миграции:** после `alembic revision --autogenerate` убедиться, что enum-поля используют `sa.Enum(..., name="...")`, а не `sa.String(...)`.

### Frontend

- **`verbatimModuleSyntax: true`** → типы через `type X`:

      import { type Task, fetchTasks } from './api/tasksApi'

- **Server state** — только TanStack Query (`useQuery`, `useMutation`).
- **HTTP** — только через `frontend/src/api/client.ts`.
- **Стили** — Tailwind + shadcn/ui. Никаких CSS-модулей.

### Общее

- **Не добавляй новые зависимости** без согласования.
- **Не меняй `.env`** и не трогай секреты.
- **Не коммить в `main` напрямую.**
- **Не переписывай архитектуру** без согласования.
- **Не используй `try/except` для валидации** (Pydantic + доменные правила).
- **Не оставляй `print(...)`** в коде (используй `logging`).
- **Не оставляй `TODO`** без задачи в `TASKS.md`.

## Инструменты

- **Терминал:** CMD (Windows).
- **Окружение:** `.venv` активируется через `..\.venv\Scripts\activate` (из `backend/`).
- **Запуск backend:** `uvicorn backend.src.main:app --reload` (из корня).
- **Запуск frontend:** `npm run dev` (в `frontend/`).
- **Тесты:** `pytest backend/tests/ -v` (из корня).
- **Линтер:** `ruff check .` + `ruff format .` (из корня).
- **Alembic:** запускать **из `backend/`**, не из корня.

### Готовые команды (для Kilo Code)

**Тесты (из корня):**

    .venv\Scripts\activate && pytest backend/tests/ -v

**Alembic (из корня, с переходом в backend):**

    cd backend && ..\.venv\Scripts\activate && alembic current
    cd backend && ..\.venv\Scripts\activate && alembic upgrade head
    cd backend && ..\.venv\Scripts\activate && alembic revision --autogenerate -m "описание"

**Ruff (из корня):**

    .venv\Scripts\activate && ruff check backend/

**uvicorn (из корня):**

    .venv\Scripts\activate && uvicorn backend.src.main:app --reload

### Важно

- **Не создавай Python-скрипты для обхода команд.** Если команда не работает — **спроси человека**.
- **Не перебирай варианты** команд больше 2-3 раз. Если не получается — остановись и спроси.
- **Используй готовые команды выше** — они проверены.

### Коммиты в CMD (Windows)

CMD плохо работает со специальными символами в сообщении коммита (`+`, `&`, `^`, `"`).

**Проблемы:**
- `git commit -m "feat(domain): add X + Y"` — символ `+` ломает команду.
- `git commit -m "add Type("foo")"` — кавычки конфликтуют.

**Как делать:**
1. `git commit --message="..."` (длинный флаг).
2. Если сообщение содержит специальные символы — использовать `git commit -F <file>`:
   - Записать сообщение в файл `commit-msg.txt`.
   - `git commit -F commit-msg.txt`.
   - Удалить файл после.
3. После коммита выполнить `git log --oneline -1` — убедиться, что сообщение правильное.
4. **Не использовать** `--allow-empty-message` как обходной путь — это маскирует проблему.

## Стиль работы

### 1. План → Утверждение → Исполнение

**Всегда:**

1. **Plan Mode.** Сначала опиши план: что, зачем, какие файлы.
2. **Жди утверждения** от человека.
3. **Agent Mode.** Только после «ок» — пиши код.

**Никогда:** не бросайся сразу писать код.

### 2. Маленькие шаги

- Одна задача — один коммит.
- После каждого шага — проверка (`pytest`, `git status`).
- Не делай **две большие задачи** в одном коммите.

### 3. Тесты обязательны

- **Всегда** для бизнес-логики (сервисы, репозитории, парсеры).
- Стиль — `AsyncMock`, `pytest-asyncio`.
- Smoke-тесты — минимум. 80% покрытия — цель.

#### Тесты роутов — httpx.AsyncClient, не TestClient

FastAPI 0.143.x + middleware (FastAPIOffline) не совместим с sync
`TestClient` — `AsyncExitStack` не инициализируется.

**Для тестов роутов:**
- `httpx.AsyncClient` + `ASGITransport`.
- Создавать отдельный `FastAPI` app для каждого теста.
- Включать роутер через `app.include_router(...)`.
- Мокать зависимости через `app.dependency_overrides`.
- **Не использовать** `TestClient`.
- **Не использовать** общий app из `main.py` — тянет middleware и БД.

**Пример:** `backend/tests/test_premises_routes.py`.

#### Тесты не удалять при проблемах

Если тесты не работают — **разобраться, а не удалять**.

**Алгоритм:**
1. Понять, почему не работает (точная ошибка, стек).
2. Найти причину (библиотека, версия, middleware).
3. Выбрать обходной путь.
4. Написать тесты заново.

**Запрещено:**
- Удалять тесты «потому что не работают».
- Пропускать тесты через `@pytest.mark.skip` без обоснования.
- Заменять тесты на «сервисы уже протестированы» — это разные слои.

### 4. Feature-ветки

- **Всегда** — от `main`.
- Название: `feat/xxx`, `fix/xxx`, `docs/xxx`.
- **Не коммить в `main` напрямую.**

**После завершения подсессии — мержить в main.**

1. `pytest` + `npm run build` — зелёные.
2. `git checkout main`.
3. `git merge <feature-branch>` (fast-forward).
4. `git push`.
5. `git branch -d <feature-branch>`.
6. `git push origin --delete <feature-branch>`.

**Почему:** иначе ветки копятся. 19 веток — это проблема.

### 5. Коммиты

Формат:

    <type>(<scope>): <короткое описание>

**Типы:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`.

Примеры:

    feat(db): add performance indexes
    fix(gitignore): stop ignoring db models
    docs(context): add ARCHITECTURE.md

### 6. Pull Request (опционально)

PR — для ревью кода. Если координатор **сам** мержит — PR не обязателен.

**Описание PR (если используешь):**

- **Что:** суть изменения.
- **Зачем:** какую задачу решает.
- **Как проверить:** шаги для ревьюера.

### 7. Обновление AI-контекста после задачи

После завершения КАЖДОЙ задачи (создание / изменение кода):

1. **Обнови `docs/context/TASKS.md`:**
   - Перенеси выполненные пункты из «В работе» в «Сделано».
   - Добавь запись в «Журнал (Changelog)» с текущей датой (формат DD.MM.YYYY).
   - Обнови раздел «Метрики проекта», если изменились числа.

2. **Обнови `docs/context/CONTEXT.md`:**
   - Раздел 2 «Уровни продукта» — если статус уровня изменился.
   - Раздел 4 «Что сделано» — если появилась новая фича / компонент.
   - Раздел 5 «Что в работе» — если задача завершена.

3. **Обнови `docs/context/API.md`** — если добавлены / изменены эндпоинты.

4. **Обнови `docs/context/DATABASE.md`** — если добавлены / изменены таблицы или поля.

5. **Включи изменения контекста в тот же коммит, что и код:**

       git add docs/context/ <изменённые-файлы-кода>
       git commit -m "<type>(<scope>): <описание> + context sync"

6. **HANDOFF.md — по маркеру [handoff] в коммит-сообщении.**

   Kilo Code обновляет `docs/context/HANDOFF.md` в двух случаях:

   1. **По запросу человека** («сохрани эстафету», «пиши HANDOFF»).
   2. **Автоматически** — если в коммит-сообщении есть маркер `[handoff]`.

   **Пример коммита с маркером:**

       git commit -m "docs(context): close session 5.2f-1 [handoff]"

   **При обнаружении маркера [handoff]:**
   - Обновить HANDOFF.md по шаблону (что было, что делаем, что дальше,
     открытые вопросы).
   - Push сделать обязательно (иначе HANDOFF недоступен в новом чате).
   - Включить HANDOFF.md в тот же коммит.

   **Без маркера [handoff]** — Kilo Code НЕ трогает HANDOFF.md, даже если
   push содержит feat/test. Это защита от шума в git-истории.

   **Почему так:** HANDOFF — межсессионная эстафета, а не лог каждой
   подсессии. Обновление по маркеру даёт человеку явный контроль: один
   маркер в конце дня/сессии, а не после каждого коммита.

**Проверка:** перед завершением задачи убедись, что:
- `docs/context/TASKS.md` — обновлён (журнал + статус).
- `docs/context/CONTEXT.md` — обновлён (если менялось что-то существенное).
- Всё в одном коммите с кодом.

**Исключение:** если задача — только чтение / анализ (аудит, отчёт), без изменений в коде — контекст не обновляется.

### 8. Подготовка новой сессии (по запросу)

Если человек говорит «подготовь новую сессию [N.M] ([название])»:

1. Скопируй `docs/templates/HANDOFF_template.md` → `docs/context/HANDOFF.md`.
2. Заполни разделы 1, 2, 3, 5 (по факту из `TASKS.md` и истории).
3. Разделы 4, 6, 7 — оставь как есть (универсальные).
4. Создай `docs/tasks/[N.M]_prompt.md` из `docs/templates/task_prompt_template.md`.
5. Обнови `TASKS.md` (раздел 2 → ссылка на новый промпт).
6. Коммит: `docs: prepare session [N.M]`.

**Важно:** шаблоны — в `docs/templates/`. Не менять их без согласования.

### 9. Первое использование паттерна — проверять в проекте

Если делаешь что-то впервые (enum в модели, JSONB-поле, ассоциативная таблица, кастомный индекс) — сначала найди существующий пример в проекте:

- `grep` по моделям, репозиториям, сервисам.
- Если пример есть — следовать ему.
- Если примера нет — выбрать паттерн, обосновать в комментарии или коммите, зафиксировать в AGENTS.md (если паттерн повторяющийся).

**Пример:** enum'ы в SQLAlchemy-моделях. Перед созданием `PremiseCategory` проверил — в проекте нет enum'ов. Выбрал паттерн `create_type=False` (безопасно для Alembic). Зафиксировал в AGENTS.md.

## Конкретные подсказки

2. **Порт репозитория** — `backend/src/domain/ports/repositories.py`.

7. **Регистрация роута** — `backend/src/main.py` + `routes/__init__.py`.
8. **Тесты** — `backend/tests/test_<name>_service.py`.

### Frontend: новая страница

1. **API-клиент** — `frontend/src/api/<name>Api.ts`.
2. **Хук** — `frontend/src/hooks/use<Name>.ts`.
3. **Страница** — `frontend/src/pages/<Name>Page.tsx`.
4. **Роутинг** — `frontend/src/main.tsx` или `App.tsx`.
5. **Компоненты** — `frontend/src/components/`.

### Миграция Alembic

    cd backend

    alembic upgrade head

**Проверить:**

- Не додумывай смысл терминов из контекста — в онтологии каждый
  термин имеет точное определение.

## Три роли (координатор — аудитор — управляющий)

Проект использует трёх участников:

| Роль | Кто | Что делает |
|---|---|---|
| **Координатор** | Kilo (Code / Orchestrator) | Ведёт подсессию, вызывает суб-агентов, коммитит (с разрешения человека) |
| **Аудитор** | Kilo (Суб-агент auditor, DeepSeek V4.1 Flash) | Проверяет план/код по чек-листу docs/tools/AUDIT_PROMPTS.md, выносит APPROVE / CHANGES REQUIRED |
| **Управляющий** | DeepSeek (чат) | Задаёт правила, решает архитектурные споры |

**Правила:**

- Аудит проводится суб-агентом `auditor` (вызов через инструмент `task` в Kilo Code). Ручные паузы не нужны.
- Координатор **не** аудирует сам себя — аудит делает отдельный суб-агент с чистым контекстом.
- Аудитор **не** меняет код. Только отчёт: `APPROVE` или `CHANGES REQUIRED`.
- `CHANGES REQUIRED` — координатор исправляет блокеры и повторяет аудит. `APPROVE` — продолжает.
- Если аудитор нашёл проблему, а координатор считает, что её нет — вопрос к Управляющему.
- Коммит — только после `APPROVE` аудитора и с разрешения человека.

**Промпты аудитора** — в `docs/tools/AUDIT_PROMPTS.md`.

## Если что-то неясно

**Спроси человека.** Не догадывайся, не выдумывай. Лучше спросить и сделать правильно, чем сделать быстро и неправильно.
