## Что нового в 7.0

- Два столпа онтологии: (1) вводные + логика + механизм вывода = структура; (2) система знает вводные → предлагает структуру → ГИП утверждает.
- Формула ядра: трёхэлементная (вводные + логика + механизм вывода).
- Механизм вывода двухуровневый: правила (вехи 1–5) + LLM (веха 6).
- 6 вех × 4 недели = 24 недели (20 недель продукт + 4 недели пилот).
- Агенты — не MVP-3, а раньше. XML — часть агента XML, не отдельная веха.
- MinIO — инструмент для документов, не веха.
- DOMAIN.md v1.1 — главный документ онтологии.

## §2. Принципы 7.0

### 2.1. Из DOMAIN.md v1.1

1. **Вводные + логика + механизм вывода = структура управления проектом.** Без механизма вывода — таск-трекер. С механизмом — соавтор.
2. **Система знает вводные → предлагает структуру → ГИП утверждает.** Это не таск-трекер. ГИП — редактор, не «кнопка ок».
3. **Механизм вывода двухуровневый.** Правила (вехи 1–5) — простые предложения. LLM (веха 6) — сложные.
4. **ГИП — редактор.** Утверждает, правит, отклоняет, утверждает списком.
5. **Осторожность предложений.** Вехи 1–5 — только явное из вводных. Веха 6 — адаптивно.
6. **Агент предлагает — ГИП решает.** Автономия — только там, где делегировано.
7. **Агенты — сотрудники с ролью.** Не фоновые процессы. Имя, роль, зона ответственности.

### 2.2. Принципы карты

1. **Веха = 4 недели = видимый результат для ГИПа.**
2. **Ценность раньше полноты.** ГИП получает пользу с первой вехи.
3. **Адаптируем, не переписываем.** Используем то, что уже сделано (6.4).
4. **Открытые вопросы решаются внутри вех.** Не откладываем на потом.
5. **Демо в конце каждой вехи.** ГИП видит результат.

### 2.3. Из 6.4 (живут)

- Домен чистый (без FastAPI/SQLAlchemy).
- Порты и адаптеры (гексагональная архитектура).
- Гибридная модель данных (системные + generic).
- ГОСТ-совместимость — фундамент.
- XML — обязательность.
- AI-контекст — часть продукта.
- Только российские ИИ-инструменты (GigaCode).
- GUID документа.
- DocumentVersion + DocumentLink.

### 2.4. Проверка характеристик на каждом шаге

**Каждая** **веха** **и** **каждая** **подсессия** **проверяются** **по** **четырём** **характеристикам** (см. `DOMAIN.md` §2.5).

**Что** **проверяется** **на** **демо** (в** **конце** **каждой** **вехи**):
- **Нативность:** сколько** **кликов** **до** **цели**? **≤ 3**?
- **Юзабилити:** сколько** **ошибок** **при** **создании** `Goal`? **≤ 1** **на** **10**?
- **Ценность:** сколько** **часов** **сэкономил** **ГИП**? **Есть** **замеры**?
- **Доверие:** сколько** **ложных** **срабатываний** **валидатора**? **≤ 10%**?

**Если** **метрика** **не** **достигнута** — **фича** **не** **принимается**. **Она** **дорабатывается** **или** **откладывается**.

### 2.5. Процесс проверки характеристик

**Проверка** — **не** **один** **раз** **в** **конце** **вехи**. **Это** **процесс**:
1. **Подсессия** — GigaCode проверяет три метрики (нативность, юзабилити, доверие) перед коммитом.
2. **Демо вехи** — ГИП проверяет все четыре метрики (включая ценность в цифрах).
3. **Пилот** — пилотный ГИП проверяет SUS, время, пропуски.

**Если метрика не достигнута:**
- **На подсессии** — не коммитить.
- **На демо** — вернуть на доработку.
- **На пилоте** — зафиксировать в отчёте, решить: доработать или отложить.

### 3.1. Топ-5 болей (из 12 интервью)

| Боль | Частота | Покрытие вехами |
|------|---------|-----------------|
| Координация смежников | 10/12 | Веха 1 (вводные), веха 2 (Action) |
| Контроль просрочек | 9/12 | Веха 5 (агент сроков) |
| Потеря задач | 8/12 | Веха 1 (Goal), веха 2 (Action) |
| Согласования | 7/12 | После пилота (§7) |
| Изменения / РВИ | 6/12 | После пилота (§7) |

### 3.2. Что закрывает продукт после вехи 5

**3 из 5 болей:**

1. **Координация смежников.** Вводные как сущности + Goal → Decision → Task → Action. ГИП видит полную картину связей.
2. **Контроль просрочек.** Агент сроков (веха 5) — напоминания, эскалация, Telegram-сводка.
3. **Потеря задач.** Action как атомарная единица с измеримым результатом. Система предлагает из вводных.

**Согласования и РВИ — после пилота** (§7).

## §5. Детализация вех 1–5 (продукт)

---

### Веха 1: Система знает вводные и предлагает цели (4 недели)

**Ценность.** ГИП видит договор, ТЗ, требования Заказчика, ИД, нормы, НПА — не как файлы, а как сущности с атрибутами. Система предлагает Goal на основе вводных. ГИП утверждает.

#### 5.1.1. Что входит

**Домен + модель + миграция:**
- Вводные как сущности: `Premise` (вводная предпосылка). Каждая категория — отдельная сущность (Договор, ТЗ, Требования, ИД, Нормы, НПА, Гос.бюрократия, Внутренние ресурсы) или одна обёртка `Premise` с полем `category` — вопрос 1.
- Goal: формулировка, срок, ответственный, приоритет, состояние (план / в работе / достигнуто / отменено).
- Связи Goal → Decision (M:N).
- Связи Goal ↔ Premise (M:N).
- Миграции Alembic.

**DTO + порты + репозитории + сервисы:**
- DTO: `PremiseSchema`, `GoalSchema`, `GoalCreate`, `GoalRead`, `GoalUpdate`.
- Порты: `PremiseRepository`, `GoalRepository`.
- Репозитории: `SqlAlchemyPremiseRepository`, `SqlAlchemyGoalRepository`.
- Сервисы: `PremiseService`, `GoalService`.
- Валидации: уникальность кода, existence checks, same project.

**DI + эндпоинты:**
- DI: `get_premise_service`, `PremiseServiceDep`, `get_goal_service`, `GoalServiceDep`.
- Роуты: CRUD для Premise, CRUD для Goal, эндпоинт «предложить Goal из вводных» (правило).
- Регистрация в `main.py`.

**Тесты:**
- Unit-тесты сервисов: `test_premise_service.py`, `test_goal_service.py`.
- Smoke-тесты маппинга: `test_premise_mapping.py`, `test_goal_mapping.py`.

**UI:**
- API-клиент: `premiseApi.ts`, `goalApi.ts`.
- Хуки: `usePremises`, `useGoals`.
- Страницы: `PremisesPage`, `GoalPage`.
- Компоненты: `PremiseCard`, `GoalCard`, `GoalForm`.
- Роутинг в `App.tsx`.

#### 5.1.2. Что переиспользуем из 6.4

- Гексагональная архитектура (домен → порты → адаптеры).
- DI-инфраструктура (dependencies.py).
- DTO-паттерн (Pydantic).
- Frontend-паттерн (API-клиент → хук → страница).
- Document-модель (DocumentType, DocumentVersion, DocumentLink) — для Premise ↔ Document.

#### 5.1.3. Открытые вопросы DOMAIN.md §11

- **[Вопрос 1]** Явная сущность «Вводная»? — Открыт. Решается в вехе 1. Варианты: (A) одна обёртка `Premise` + категория как поле; (B) отдельные сущности по категориям (Договор, ТЗ, ИД, НПА, Ресурсы). Решение — после анализа сценариев.
- **[Вопрос 13]** Механизм вывода. — Веха 1: правила для Goal. Веха 2: правила для Action. Веха 3: правила для Decision. Веха 4: правила для RFI. Веха 6: LLM.
- **[Вопрос 14]** Утверждение. ГИП — редактор. Утверждает по одному, списком, с правками, отклоняет. Конкретные механики — в вехе 1.

#### 5.1.4. Выход (демо)

ГИП загружает договор → система предлагает Goal «Сдать том 7 в экспертизу» → ГИП утверждает → видит Goal в UI.

#### 5.1.5. Что НЕ входит

- Decision, Task, Action (веха 2–3).
- RFI (веха 4).
- Агент сроков (веха 5).
- LLM (веха 6).

#### 5.1.6. Риски

- Вводные — разнородные. Сложно свести к одной модели.
- Митигация: каждая категория — отдельная сущность с общим интерфейсом.

#### 5.1.8. Агент-валидатор (часть вехи 1)

Проверяет предложения (от смежников, от системы) на **доказанность**:
- Есть ли **два места** в документе (источник и следствие)?
- Есть ли **источник** у каждой цифры?
- Если данных нет — **предложить RFI** (запрос), а не «решение».
Работает на правилах (веха 1–5), без LLM.

#### 5.1.9. Матрица смежников (часть Вехи 1)

**Правила вывода связей** (а не «6 шаблонов»). Если в договоре есть два раздела — система **предлагает** связь между ними, указывая **что** согласовать. ГИП утверждает.

| Смежник | Что согласовать | Сигнал риска (если не согласовано) |
|---|---|---|
| **АР ↔ ОВ** | Отверстия и шахты под воздуховоды, венткамеры, дымоудаление | Пробивка по факту, простой, переделка узла |
| **АР ↔ КЖ** | Проёмы в несущих, нагрузки от перегородок, оси и отметки | Пересчёт узла, усиление |
| **АР ↔ ВК** | Стояки, короба, санузлы, гидроизоляция, уклоны полов | Перенос санузла на РД |
| **АР ↔ ЭО** | Щитовые, ниши под щиты, трассы, помещения связи | Перепланировка под щит |
| **АР ↔ ПБ** | Пути эвакуации, преграды, огнестойкость, зоны безопасности | Возврат с экспертизы |
| **АР ↔ ПЗУ** | Посадка здания, отметки входов, отступы, благоустройство | Несоответствие ГПЗУ |
| **ОВ ↔ КЖ** | Нагрузки на перекрытия от оборудования (200 кг – 3 т) | Пересчёт плиты, усиление |
| **ОВ ↔ ЭО** | Электропитание: мощность, фазы, IP, способ ввода | Переделка кабеля, щита |
| **ОВ ↔ ТХ** | Категории помещений по СП 12.13130 | Противодымка не заложена |
| **ОВ ↔ ПБ** | Противодымная вентиляция по СП 7.13130 | Возврат с экспертизы |

**Три уровня проверки для каждой связи:**
- **Уровень 1** — контроль входа (что прислали).
- **Уровень 2** — механическое сравнение (что изменилось).
- **Уровень 3** — инженерное суждение (что остаётся человеку).

**Стоп-правила** (6 признаков): исчезла треть позиций, сдвиг к оси, одно отверстие внутри другого, верх упирается в плиту, изменение после бетонирования, размер «с запасом».

**Форма ответа** (6 статусов): принято, принято с обрамлением, замечание, отклонено, перенести, срок ответа.

**Пример правила:**
> Если в договоре есть «АР» и «ОВ» → предложить связь «АР ↔ ОВ» с формулировкой: «Согласовать отверстия под воздуховоды D≥200 мм, венткамеры, дымоудаление». Сигнал риска: «Пробивка по факту, простой».

#### 5.1.10. Протокол 2–3 прогонов (часть Вехи 1)

Агент-валидатор (см. §5.1.8) работает **по протоколу 2–3 прогонов**. Это значит: он **не** возвращает «один ответ», он возвращает **свод**:
- **3/3** — подтверждено (в приоритет).
- **2/3** — требует проверки.
- **1/3** — требует ручной проверки.

**Граница:** протокол работает **только** для формальных проверок (полнота, согласованность, ссылки). Для **расчётов** и **графики** — он **не применяется** (там нужен инженер).

**Что это даёт:** снижает риск пропуска (если модель не увидела в одном прогоне, но увидела в двух — это сигнал). И снижает риск ложных срабатываний (если 1/3 — скорее всего, ошибка модели).

#### 5.1.11. Ревизия и молчаливая правка (часть Вехи 1)

**Проблема:** смежник **изменил** данные (сдвинул отверстие на 250 мм) и **не** **написал**. Это **не** «нет данных». Это **`changed_silently`**.

**Что делать:**
1. **Зафиксировать** ревизию (`Revision`).
2. **Сравнить** с предыдущей (`Change`).
3. **Проверить** `notified` — если **не** **уведомил** — `changed_silently`.
4. **Проверить** стоп-правила (6 признаков).
5. **Выдать** решение (`RevisionDecision`): принято / с обрамлением / замечание / отклонено / перенести / срок ответа.

**Комплекс задач** (не только отверстия):
- **Отверстия** — сдвиг к оси, одно внутри другого, верх упирается в плиту.
- **Нагрузки** — изменение без уведомления.
- **Проёмы** — сдвиг или изменение размера.
- **Стояки** — перенос без уведомления.
- **Щиты** — изменение места без уведомления.
- **Трассы** — изменение без уведомления.

**Граница:** система **находит** изменения и **подсвечивает** стоп-сигналы. **Решение** — **за** **ГИПом**.

#### 5.1.12. Дашборд ГИПа (доработка Вехи 1, очередь после Вехи 3)

**Проблема:** **сейчас** **первый** **экран** — **канвас** (**красиво**, **но** **при** **100** **целях** — **каша**). **ГИП** **утром** **хочет** **видеть** «**что** **горит»**, **а** **не** **все** **цели**.

**Что** **делаем:**
- **Первый** **экран** **после** **входа** — **дашборд** (**не** **канвас**).
- **Блоки:**
  - **ПРОСРОЧЕНО** (N) — **красным**, **топ-10**.
  - **СЕГОДНЯ** (M) — **жёлтым**.
  - **НА** **ЭТОЙ** **НЕДЕЛЕ** (K) — **синим**.
  - **ТРЕБУЕТ** **ПРОВЕРКИ** (`requires_check`) — **оранжевым**.
  - **ИЗМЕНЕНО** **МОЛЧА** (`changed_silently`) — **фиолетовым**.

## §6. Детализация вехи 6 (Пилот, 4 недели)

**Ценность.** LLM (Qwen 2.5 7B) как часть механизма вывода. XML (схемы Минстроя). MinIO (если не в вехе 4). Auth (JWT + Argon2). Деплой на VPS. Лендинг. Комплаенс 152-ФЗ.

#### 6.1. LLM (Qwen 2.5 7B)

- Развёртывание на VPS (16 GB RAM, 8 vCPU).
- Подключение к агентам (механизм вывода).
- Распознавание структуры в тексте.
- Сложные предложения: «В этом письме — три решения».
- Валидация по XSD (если не в вехе 4).

#### 6.1.1. Локальный RAG (часть Пилота)

**Что это:** локальная модель (MiMo 7B / Qwen 2.5 7B) + база знаний (нормативы, регламенты, прошлые проекты). Модель **ищет** в базе, потом **отвечает**.

**Зачем:** для чувствительных данных (152-ФЗ), которые нельзя в облако.

**Требования:** ОЗУ от 16 ГБ (для 7B), видеокарта — опционально (GeForce RTX 3070 Ti или аналогичная). Работает на ноутбуке или сервере.

**Граница:** RAG **не** заменяет LLM. Он **дополняет** — для поиска по базе. Для сложных рассуждений — облачная модель (Claude / MiMo V2.5-Pro). Гибрид: локальная модель для приватных сверок, облачная — для сложных.

#### 6.1.2. Светофор данных (часть Пилота)

**Что это:** классификация данных по трём категориям — что можно отдавать в облако, что только локально, что нельзя вообще.

| Категория | Что | Куда |
|---|---|---|
| **🟢 Зелёный** | Общие технические сведения, обезличенные тексты, открытые нормативы | Любой разрешённый ИИ-сервис |
| **🟡 Жёлтый** | Спецификации, ВОР, сметы (без заказчика и адреса), текстовые части ПД (после обезличивания) | Только после обезличивания (чек-лист 22 шага) |
| **🔴 Красный** | Полные комплекты ПД с реквизитами, договоры с суммами, персональные данные, КИИ | Только локальный ИИ или вручную |

**Граница:** светофор — **не** замена 152-ФЗ, а **рабочий инструмент** для специалиста. Каждый перед отправкой в ИИ отвечает: «Какого цвета эти данные?»

#### 6.1.3. Гейты ГГЭ (часть Пилота)

**Что это:** три контрольные точки перед подачей в Главгосэкспертизу. Позволяют не потерять недели на «подача → отказ → доработка».

| Гейт | Когда | Что проверяем | Ответственный |
|---|---|---|---|
| **Г-0 «Старт»** | После утверждения задания | Состав ПД, формат, сметный метод, идентификация (Карта А) | ГИП |
| **Г-1 «Разработка»** | На рабочих версиях | СРО/НРС, XML, ВОР, оглавление, титулы = Карта А | Нормоконтроль, сметчик, юрслужба |
| **Г-2 «Предподача»** | Перед направлением в ГГЭ | УКЭП/МЧД, валидация XML, согласование смет | Координатор, ЭДО/УКЭП |

**Граница:** гейты — **не** замена экспертизы, а **профилактика** отказов по формальным признакам (несовпадение реквизитов, подписи, формат).

#### 6.1.4. Стоп-правила и форма ответа (часть Пилота)

**Стоп-правила** (6 признаков, когда **надо** **остановиться** и **выяснить** **голосом**):
1. Исчезла треть позиций и больше (скорее всего, прислали часть таблицы).
2. Отверстие сдвинулось к оси (ось — линия сетки, а не грань).
3. Одно отверстие внутри другого (либо один проём на две сети, либо ошибка).
4. Верх отверстия упирается в плиту (это уже проём, расчётная схема другая).
5. Изменение после бетонирования захватки (не правка чертежа, а сверление).
6. Размер «с запасом» (1000×1000 вместо 600×400 ослабляет конструкцию).

**Форма ответа** (6 статусов, что **уходит** **смежнику**):
- **Принято** — перечень ID, которые идут в чертёж без изменений.
- **Принято с обрамлением** — ID и ссылка на узел усиления, лист КЖ.
- **Замечание** — ID, в чём вопрос, что прислать дополнительно.
- **Отклонено** — ID и причина (попадает в балку, в зону продавливания).
- **Перенести** — ID и предлагаемое место (встречное задание).
- **Срок ответа** — дата, к которой нужен ответ.

**Что фиксировать у себя:** по каждой позиции — дата получения, дата ответа, решение, кто принял, лист КЖ с номером изменения.

#### 6.1.5. Power Query-подобный механизм (часть Пилота)

**Что это:** механизм **сравнения** двух ревизий таблицы (без макросов, на штатном Power Query).

**Запрос 1 — контроль входа:**
- Сколько позиций в А и Б.
- Совпадает ли состав колонок.
- Есть ли повторы ID.
- Доля исчезнувших (стоп-правило: > 30%).

**Запрос 2 — сравнение:**
- Развернуть обе таблицы в пары «ID + поле + было + стало».
- Найти: снято, добавлено, изменено.
- Свернуть (Distinct) — одна строка на позицию.

**Граница:** механизм **не** **хранит** историю (это **сравнение** **двух** **таблиц**, **а** **не** **журнал**). **Не** **понимает** **смысл** **полей** (для **него** «Ширина, мм» — **просто** **колонка**). **Не** **сопоставляет** **позиции** **по** **геометрии** (если **смежник** **перенумеровал** **строки** — **сравнение** **покажет** «всё** **снято** **и** **всё** **добавлено»).
