## 1. Резюме проекта

**ГИП-Ассистент** — облачная (SaaS) система управления проектной разработкой для микро-студий, частных ГИПов и проектных институтов.

**Стек:**

| Слой | Технология |
|------|-----------|
| Backend | FastAPI + SQLAlchemy 2.0 async + PostgreSQL 15 + Alembic |
| Frontend (приложение) | React 18 + Vite + TypeScript + shadcn/ui + TanStack Query |
| Website (лендинг) | Next.js 14 + TypeScript + shadcn/ui |
| Bot | aiogram 3.x (Telegram) |
| LLM | Qwen 2.5 7B (локально на VPS, 16+ GB RAM) |
| Storage (документы) | MinIO AIStor Free (S3-совместимое) |
| XML-формат | lxml + xmlschema (валидация по XSD Минстроя) |
| AI-контекст | Markdown + GitHub Actions |
| AI-инструменты (разработка) | GigaCode (PyCharm) + самописный агент на GigaChat API |
| Инфра | Docker Compose + Nginx + GitHub Actions |

**Ключевая идея:**

> ГИП-Ассистент — не заставляет менять рабочий процесс. Мы встраиваемся в существующий Excel и превращаем его в удобный интерфейс с универсальными сущностями. На выходе — документы в формате, требуемом государственной экспертизой.

**Ключевые барьеры MVP:**

1. Ручной ввод статусов. Решается через матрицу смежников и ежедневную Telegram-сводку.
2. Обязательный XML-формат ПД. С 2025-2026 гг. ТЗ и ПЗ сдаются в XML. Без этого продукт не купят институты.
3. Работа с ИИ и будущими разработчиками. Без единой системы AI-контекста каждый новый чат и каждый новый разработчик начинают с нуля.

**Юридическое лицо:** ИП на УСН 6%.

**Бренд:** ГИП-Ассистент.

**Товарный знак:** «ГИП-Ассистент» + «GIP Assistant», классы МКТУ 09, 42, 35. Подача сразу с ИП.

**Разработка:** своими силами с помощью ИИ (GigaChat, Copilot). Фрилансер не нужен.

**Value Proposition (для директора, демонстрация — через ГИПа):**

> ГИП-Ассистент — единая среда, в которой ГИП ведёт все свои проекты: запросы Заказчику, задачи смежникам, тома, согласования, документы. Директор видит, где горят сроки, без совещаний. Документы формируются в XML и готовы к отправке в экспертизу.

**Дата старта:** 1 ноября 2026.

## 2. Что изменилось с версии 5.0

### 2.1. Версия 5.0 (заморожена)

**MVP = 4 функции:**

1. Импорт Excel
2. Матрица смежников
3. Telegram-сводка
4. Скрипт продажи директору (лендинг)

**Проблема:** закрывал 2 из 5 главных болей ГИПа. Ни один ГИП не заплатит за матрицу и таблицу задач — он ведёт несколько проектов в разных стадиях, и ему нужны все рабочие сущности.

### 2.2. Версия 6.4 (текущая)

**Что сделано за 2 дня (факт):**

- Универсальный парсер Excel (merged cells, автопоиск шапки, serial-даты)
- API импорта (preview / confirm / logs)
- UI импорта (dropzone, селектор шапки, маппинг колонок)
- TaskList (500+ задач, фильтры, inline-редактирование)
- Матрица смежников (10×10, 14 ячеек, цвета, диалоги)
- Страница задач пары (группировка по срочности)
- Telegram-бот (код готов, работает через прокси)
- 39 тестов (pytest)

**Что меняем относительно 5.0:**

**Было (5.0):** фиксированные модули под конкретные шаблоны.

**Стало (6.4):** универсальные сущности — ГИП сам создаёт свои типы (ИД, Запросы, Протоколы, Тома, Письма), импортирует любые Excel, работает в привычном формате.

**Плюс новое в 6.4:**

- Поддержка XML-формата для сдачи документов в экспертизу
- AI-контекст для работы с ИИ и будущими разработчиками
- Стратегия работы с ИИ-агентами на GigaChat

**Почему:**

> ГИПы работают в разных конторах, у каждой свой Excel-шаблон. Если мы делаем фиксированные модули — мы не масштабируемся. Универсальное ядро — конкурентное преимущество и экономия 2 недель на каждого нового клиента. Поддержка XML — обязательное требование для работы с государственной экспертизой. AI-контекст — обязательное условие для масштабирования команды и эффективной работы с ИИ.

## 3. Стратегическое изменение архитектуры

### 3.1. Гибридная модель данных

**Системные сущности (фиксированные):**

| Сущность | Назначение |
|----------|-----------|
| Project | Проект |
| Task | Задача (участвует в матрице смежников) |
| CrossTask | Ячейка матрицы |
| ImportLog | Лог импорта |
| User, Executor | Пользователи |
| Notification | Уведомления |
| XMLSchema | Метаданные схем Минстроя |
| XMLDocument | Сформированные XML-документы |
| Document | Карточка документа (ГОСТ) |
| DocumentVersion | Версия файла |
| DocumentLink | Связь между документами |
| DocumentType | Справочник типов |

**Пользовательские сущности (generic):**

| Сущность | Назначение |
|----------|-----------|
| EntityType | Тип («Исходные данные», «Запросы», «Тома») |
| Entity | Экземпляр («ТУ на водоснабжение», статус «Нет») |

**Хранение данных generic:**

- `EntityType.schema` — JSONB (описание полей)
- `Entity.data` — JSONB (значения)
- `EntityType.xml_schema_code` — код схемы Минстроя (для типов, связанных с XML)
- GIN-индексы для быстрого поиска

**Почему гибрид:**

1. Матрица смежников требует фиксированных полей (`section_code`, `to_section_code`). Это системная фича, её нельзя делать generic.
2. Остальное (ИД, Запросы, Тома) — произвольная структура. Здесь generic.
3. Гибрид = готовый код для матрицы + гибкость для всего нового.

### 3.3. Документы и хранилище

**Хранилище файлов: MinIO AIStor Free.**

**Обоснование выбора:**

Ситуация с MinIO кардинально изменилась в 2025-2026:

- Май 2025: из Community Edition удалена админ-консоль
- Октябрь 2025: остановлена публикация Docker-образов
- Декабрь 2025: объявлен maintenance mode
- Февраль 2026: репозиторий архивирован
- CVE-патчи больше не выходят → неприемлемо для коммерческого продукта

**Решение:** используем MinIO AIStor Free:

- Бесплатно для single-node
- Полный S3 API — совместим с любыми клиентами
- Актуальные сборки и CVE-патчи
- Полная админ-консоль (IAM, политики, мониторинг)
- Docker-образ: `minio/aistor`
- Переход безболезненный — код на S3 API не меняется

**Ограничения AIStor Free:**

- Single-node (для MVP достаточно)
- Требует регистрации лицензии (бесплатной)
- «Redistribution prohibited» — не распространяем, хостим сами

**Для on-premise (MVP-5):**

- Клиент потребует open-source → миграция на SeaweedFS или Ceph
- Или AIStor Enterprise (от $96 000/год — только для крупных)
- Заложено в резерв бюджета (40 000 ₽)

**Архитектура хранения:**

- Файлы — MinIO AIStor (S3 API)
- Метаданные — PostgreSQL (таблица `documents`)
- Привязка — к проекту, сущности, задаче
- Ссылки — presigned URLs с TTL

**Что делаем в MVP:**

- Модель Document + DocumentVersion + DocumentLink + DocumentType (см. раздел 16)
- Справочник document_types (сиды: чертёж, схема, ПЗ, ведомость, УЛ, ТЗ, спецификация, расчёт)
- GUID документа (постоянный)
- Загрузка / скачивание / удаление
- Прикрепление к проекту, сущности, задаче
- Версионирование файлов (v1.0, v1.1, v2.0) + `is_current`
- Связи между документами (appendix, reference, replaces, version_of)

**Что НЕ делаем в MVP:**

- Совместное редактирование
- Индексация содержимого (это MVP-3 с LLM)
- Шифрование на клиенте (можно добавить в MVP-2)

### 3.4. Электронный формат проектной документации (XML)

**Обязательное требование законодательства:**

С 2025-2026 годов поэтапно вводится обязательная сдача проектной документации в машиночитаемом формате XML:

- С июля 2025 — Задание на проектирование (ТЗ) в XML
- С января 2026 — Пояснительная записка (ПЗ) в XML v1.06
- С мая 2026 — Пояснительная записка к сметной документации в XML
- С 2026 — Локальные сметные расчёты (ЛСР) и Ведомости объёмов работ (ВОР)
- К 2030 — полный перевод проектной документации в машиночитаемый формат

**Почему это критично для продукта:**

Без поддержки XML продукт не купят проектные институты. Это не «дополнительная фича», а обязательное требование для работы с государственной экспертизой.

**Стратегическое решение:**

ГИП-Ассистент — это «мозг проекта». Он хранит структурированные данные (задачи, запросы, статусы, документы, тексты). XML — это «выходной формат» для сдачи в экспертизу. Наша задача — автоматизировать трансляцию человеко-читаемых данных в машиночитаемый формат.

**Ключевые принципы:**

1. **Мы не конкурируем с ЕЦПЭ.** Единая цифровая платформа экспертизы (ЕЦПЭ) — проприетарная система Главгосэкспертизы. Её код закрыт и не подлежит копированию. Мы строим клиентскую часть экосистемы — рабочий инструмент для ГИПа, который готовит данные к отправке в ЕЦПЭ.

2. **Мы используем открытые стандарты.** XML-схемы публикуются на сайте Минстроя России (`minstroyrf.gov.ru/tim/xml-skhemy/`). Это официальный источник схем для формирования документов. Мы свободно их используем.

3. **Мы кэшируем схемы у себя.** Схемы скачиваются с сайта Минстроя, хранятся в БД, проверяются на обновление при каждом обращении к модулю экспорта. Это гарантирует актуальность без постоянной зависимости от внешнего сервиса.

4. **Мы валидируем перед выгрузкой.** Сформированный XML обязательно проверяется по актуальной XSD-схеме до того, как отдать файл ГИПу. Это отсекает 90% ошибок, из-за которых документ «отлетел бы» на экспертизе.

5. **Архитектура API-first.** Модуль XML работает через чёткий API. Это позволяет в будущем легко подключиться к ЕЦПЭ или другим системам для автоматической отправки документов.

**Что делаем в MVP-2:**

- Модуль «Электронный документ ПД» — тип сущности со схемой Минстроя
- Модуль «Экспорт XML» — генерация из данных проекта
- Модуль «Валидация XSD» — проверка перед выгрузкой
- Сервис получения и обновления схем с сайта Минстроя

**Что НЕ делаем в MVP-1.5:**

- Автоматическая отправка в ЕЦПЭ (MVP-3 или позже — требует интеграции с API Главгосэкспертизы)
- Все разделы ПД (только ТЗ и ПЗ — самые критичные)
- Редактор XML в интерфейсе (только формирование и валидация)

## 5. Три уровня продукта

### 5.1. Уровень 1 — Универсальные сущности (MVP)

**Что даёт:**

- ГИП сам создаёт типы: «Исходные данные», «Запросы», «Протоколы»
- Настраивает поля под свои привычки
- Импортирует любой Excel
- Работает в удобном интерфейсе

**Что НЕ даёт:**

- Готовых шаблонов (это Уровень 2)
- Работы с LLM (Уровень 3)

**Технически:**

- `EntityType` + `Entity` + JSONB + GIN
- CRUD API
- UI: конструктор + таблица + фильтры

**Оценка:** 5-6 дней.

### 5.2. Уровень 2 — Библиотека шаблонов (MVP)

**Что даёт:**

- ГИП выбирает готовый шаблон — не создаёт с нуля
- Экономит 1-2 часа на каждом проекте

**Шаблоны в MVP:**

| № | Шаблон | Назначение |
|---|--------|-----------|
| 1 | ИД_ПД | Исходные данные для проектирования |
| 2 | ИД_РД | Исходные данные для рабочей документации |
| 3 | Запросы | Исходящие / входящие запросы Заказчику |
| 4 | Тома | Производство (статусы, % готовности) |
| 5 | Письма | Исходящая корреспонденция |
| 6 | Протоколы | Протоколы совещаний |

**Как работает:**

- В UI — галерея шаблонов
- ГИП кликает → копируется в проект
- ГИП правит поля под себя

**Оценка:** 2-3 дня.

### 5.2.5. Уровень 2.5 — XML-формат ПД (MVP-1.5)

**Что даёт:**

- ГИП формирует ТЗ и ПЗ в XML
- Система валидирует по XSD Минстроя
- Готовый файл — скачивается

**Документы в MVP-1.5:**

1. **ТЗ** (Задание на проектирование) — обязательно с июля 2025
2. **ПЗ** (Пояснительная записка) — обязательно с января 2026, версия 1.06

**Как работает:**

1. ГИП создаёт тип сущности «Электронный документ ПД»
2. Выбирает нужную схему из списка (ТЗ или ПЗ)
3. Заполняет поля, соответствующие элементам XML-схемы
4. Нажимает «Экспорт XML» — система формирует файл
5. Валидация по XSD → если ошибки, показать их
6. Скачивание готового XML

**Технически:**

- Сущность `XMLSchema` — метаданные схем Минстроя
- Сущность `XMLDocument` — сформированные XML
- Расширение `EntityType` — поле `xml_schema_code`
- Сервис `XMLService` — генерация и валидация
- Сервис `SchemaService` — скачивание и обновление схем

**Оценка:** 2 недели (отдельный этап MVP-1.5).

### 5.3. Уровень 3 — LLM-ассистент (MVP-3)

**Что даёт:**

- RAG по загруженным документам
- Генерация черновиков писем, отчётов, ТЗ

- Ответы на вопросы по проекту

**Технически:**

- Qwen 2.5 7B (локально на VPS, 16 GB RAM)
- pgvector для эмбеддингов
- MinIO для файлов
- FastAPI + llama-cpp-python или vLLM

**Требования к VPS:**

| Параметр | Минимум |
|----------|---------|
| RAM | 16 GB |
| CPU | 8 vCPU |
| Диск | 80 GB SSD |
| GPU | опционально |

**Оценка:** 4-5 недель (MVP-3).

### 9.2. Добавляем в 6.2

21. Универсальные сущности — ядро продукта. ГИП сам настраивает типы под свои привычки.
22. Библиотека шаблонов — быстрый старт. ГИП выбирает готовое, не создаёт с нуля.
23. Документы — на S3/MinIO AIStor. Файлы отдельно от БД. Метаданные — в БД.
24. LLM — локально. Qwen 2.5 7B, никаких облаков для конфиденциальных данных.
25. Гибридная модель данных. Системные сущности (Task, CrossTask) + пользовательские (Entity).
26. **XML — обязательный формат ПД.** С 2025-2026 гг. ТЗ и ПЗ сдаются в XML. К 2030 — вся ПД. Без поддержки XML продукт не купят институты.
27. **Мы — клиентская часть экосистемы ЕЦПЭ.** Мы не конкурируем с Главгосэкспертизой, а готовим данные для её платформы. Используем открытые схемы Минстроя.
28. **Схемы Минстроя — кэшируем у себя.** Скачиваем с официального сайта, храним в БД, проверяем обновление при каждом обращении к модулю экспорта.
29. **AI-контекст — часть продукта.** `docs/context/` — источник правды для ИИ и будущих разработчиков. Пишется с первого дня, не задним числом.
30. **Документация для ИИ ≠ документация для людей.** `CONTEXT.md` — 2 страницы. Дорожная карта — 60 страниц. Разные задачи.
31. ИИ-инструменты — только с официальной поддержкой в РФ. GigaCode (PyCharm) + самописный агент на GigaChat API. Без Claude Code и Cursor (иностранные, риск блокировки).
32. **Правила для ИИ — в `AGENTS.md`.** Единый файл для Cursor, Continue, Cline. Читается перед началом работы.
33. ГОСТ-совместимость — фундамент, не «фича для экспертизы». Документы хранятся по нормам с первого дня.
34. ЭП — внешний сервис. Мы храним только метаданные подписи (signed_by, signed_at, signature_hash).
35. GUID документа — постоянный. Не меняется при выпуске новых версий. Версии — дочерние сущности.
36. DocumentVersion + DocumentLink — разделяем карточку и файл. Файловые атрибуты (хеш, формат, размер) — в версии.

### 11.2. «ИИ-на-документах» — новая категория

**Стартапы, которые:**

- Загружают ИРД, договоры, ТЗ, протоколы
- Прогоняют через GPT-4o / локальную LLM
- Переводят в JSON без БД
- Генерируют письма, отчёты, задачи

**Их преимущества:**

- Быстрый старт
- Нет необходимости настраивать структуру
- Работает с любым документом

**Их слабости:**

- Нет истории — что было в прошлой версии?
- Нет связей — протокол не связан с задачами
- Нет валидации — LLM может выдать «красивый, но неверный» JSON
- Не масштабируется — 5 проектов × 20 документов = 300 JSON без структуры
- Облачные LLM — данные уходят третьей стороне

### 11.2.5. Сервисы формирования XML для экспертизы

**Что делают:**

- Онлайн-сервисы Главгосэкспертизы (формирование ПЗ и ТЗ)
- Сторонние разработки (платные сервисы для проектных организаций)
- Локальные решения (устанавливаются на серверы институтов)

**Их преимущества:**

- Узкая специализация (только XML)
- Актуальные схемы Минстроя
- Соответствие требованиям ГГЭ

**Их слабости:**

- Не связаны с рабочим процессом ГИПа — данные нужно вводить отдельно
- Нет единой базы данных — нельзя переиспользовать информацию из задач, запросов, документов
- Дорого — платные подписки, интеграция
- Разрознены — разные сервисы для разных типов документов

**Наше преимущество:**

ГИП-Ассистент = единая база данных + рабочий процесс + формирование XML. ГИП не вводит данные дважды: он работает в системе, а XML формируется из уже имеющихся данных.

### 11.3. Наше преимущество

**ГИП-Ассистент = БД + структура + LLM + XML:**

1. БД хранит структуру — типы, поля, связи
2. LLM обрабатывает текст — извлекает, генерирует
3. RAG ищет в прошлых документах
4. Локальная LLM — конфиденциальность
5. XML формируется автоматически из данных проекта

**Ключевая фраза для продажи:**

> «Мы не заставляем вас менять Excel. Мы встраиваемся в него и превращаем в удобный интерфейс. А когда понадобится ИИ — он уже встроен и работает локально, ваши данные никуда не уходят. Документы формируются в XML и готовы к отправке в экспертизу».

### 11.4. Позиционирование

**Мы не:**

- Замена CAD (не конкурируем с Vitro-CAD)
- Замена документооборота (не конкурируем с TDMS)
- Замена PM-систем (не конкурируем с Directum)
- Замена ЕЦПЭ (не конкурируем с Главгосэкспертизой)

**Мы:**

- Инструмент ГИПа для управления проектной разработкой
- Единая среда для всех рабочих сущностей
- Работает в привычном Excel-формате
- С встроенным локальным ИИ
- С автоматическим формированием XML для экспертизы

## 15. AI-контекст и работа с ИИ

### 15.1. Зачем это нужно

**Проблема:**

При разработке с помощью ИИ (GigaChat, GigaCode, PyCharm AI) каждый новый чат начинается с нуля. ИИ не знает:
- Что уже сделано
- Какая архитектура
- Какие правила
- Какие задачи в работе

**Решение:** единая система `docs/context/` — источник правды для ИИ-ассистентов и будущих разработчиков.

### 15.2. Сценарии использования

**Сценарий 1. Новый чат с ИИ**

ГИП открывает новый чат, копирует `docs/context/CONTEXT.md` → вставляет первым сообщением. ИИ **сразу понимает** проект.

**Сценарий 2. Второй разработчик**

Новый backend-разработчик открывает репозиторий, читает:
- `CONTEXT.md` — что за продукт
- `ARCHITECTURE.md` — как устроен код
- `DATABASE.md` — схема БД
- `API.md` — эндпоинты
- `RULES.md` — правила кода

**Понимает проект за 1 час** вместо 2 дней.

**Сценарий 3. AI-ассистент в PyCharm**

PyCharm 2026 имеет встроенный AI Assistant. Если добавить `docs/context/` в Project Context — **все запросы к ИИ учитывают актуальную документацию** автоматически.

**Сценарий 4. Партнёр / инвестор**

Техническая документация проекта — в одном месте, структурирована, актуальна.

### 15.3. Структура `docs/context/`

```
docs/context/
├── CONTEXT.md          # Резюме проекта для ИИ (2 страницы)
├── ARCHITECTURE.md     # Структура, слои, стек
├── DATABASE.md         # АВТО: схема БД из SQLAlchemy
├── API.md              # АВТО: OpenAPI из FastAPI
├── RULES.md            # АВТО: правила из ruff
├── TASKS.md            # Что сделано / в работе / дальше
└── README.md           # Как этим пользоваться
```

### 15.4. Что автоматизируется

| Файл | Источник | Триггер обновления |
|------|----------|-------------------|
| `DATABASE.md` | SQLAlchemy → sqlacodegen | Изменение `backend/src/adapters/db/models/**` |
| `API.md` | FastAPI → `/openapi.json` | Изменение `backend/src/adapters/api/routes/**` |
| `RULES.md` | pyproject.toml → ruff | Изменение `pyproject.toml` |

**Механизм:** GitHub Actions обновляет эти файлы при каждом push в main.

### 15.5. Что пишется вручную

| Файл | Кто | Когда |
|------|-----|-------|
| `CONTEXT.md` | ГИП / тимлид | При стратегических изменениях |
| `ARCHITECTURE.md` | ГИП / тимлид | При архитектурных изменениях |
| `TASKS.md` | ГИП / тимлид | Перед новым чатом с ИИ |

### 15.6. Почему это важно для масштабирования

**Через 6 месяцев:** наняли второго разработчика → не надо объяснять всё лично.

**Через год:** AI-ассистенты станут стандартом → все используют наш контекст.

**Через 2 года:** open-source или партнёрство → репозиторий понятен из коробки.

**Всегда:** новый чат с ИИ → не надо пересказывать контекст вручную.

## 15.9. ИИ-агенты и автоматизация разработки

**Тренд 2025-2026:** переход от «умного автодополнения» к «постановке задачи». ИИ-агент сам пишет код, тесты, документацию, создаёт Pull Request.

**Что реально работает:**

- **GigaCode в PyCharm** — IDE-плагин от Сбера, автодополнение и простые задачи
- **Самописные агенты на GigaChat API** — для автономных задач, полный контроль

**Что НЕ работает так, как в маркетинге:**

- «Один промпт — готовая фича» — только 70-80% работы
- «8 агентов параллельно» — конфликты, дрейф архитектуры, дорого по токенам
- «Разработчик только ревьюит» — архитектура и сложные фичи — за человеком

**Стратегия для ГИП-Ассистент: гибрид**

**ИИ-агент (в IDE):**

- CRUD-код
- Тесты
- Простая документация
- Рефакторинг

**Человек + чат с ИИ:**

- Архитектурные решения
- Сложные фичи (XML, LLM, матрица)
- Юридические / комплаенс
- Стратегические документы

**Фундамент для агента — `docs/context/`:**

Без контекста агент делает мусор. С контекстом — работает предсказуемо.

**Этапы внедрения:**

- **MVP, Неделя 1-2:** docs/context/ + AGENTS.md + GigaCode + самописный ИИ-агент.
- **MVP, Недели 2-5:** все рутинные задачи кодинга — через агента (UI конструктора, шаблоны, MinIO, Auth, XML).
- **MVP-2:** background-агенты (BugBot, Context-keeper).
- **MVP-3:** sub-агенты (XML-validator, Test-writer, Doc-keeper).

**Риски:**

- **Стоимость:** автономные агенты жгут токены. Нужны лимиты.
- **Дрейф архитектуры:** агент не читает `RULES.md` → код становится кашей.
- **Сложные фичи:** XML, LLM, матрица — требуют прямого участия человека.
- **Комплаенс:** не делегировать агенту.

## 15.10. ИИ-инструменты разработки: GigaCode + самописный агент

- **GigaCode в PyCharm** — для простых задач (автодополнение, рефакторинг, docstrings).
- **Самописный агент на GigaChat API** — для автономных задач (миграции, тесты, эндпоинты).

Оба работают через российский контур, оплата рублями, не требуют VPN.

### 15.10.1. Почему НЕ Claude Code и НЕ Cursor

**Claude Code:**

- Anthropic официально не поддерживает РФ.
- С 2026 — массовые блокировки российских аккаунтов.
- Оплата требует иностранной карты или посредников.
- Использование VPN повышает риск блокировки.
- Потеря аккаунта = потеря всего рабочего контекста.

**Cursor:**

- Требует оплаты через иностранные карты.
- Менее прозрачен в отношении российских пользователей.
- Дороже, чем GigaCode (при схожем качестве на простых задачах).
- Интеграция с GigaChat через `gpt2giga` **возможна**, но добавляет прослойку.

**Решение:** только инструменты с официальной поддержкой в РФ.

### 15.10.2. Вариант A: GigaCode в PyCharm

**Что это:** официальный плагин от Сбера для PyCharm / IntelliJ IDEA. Аналог GitHub Copilot, но на GigaChat.

**Для каких задач:**

- Автодополнение кода (in-line).
- Генерация docstrings и комментариев.
- Простой рефакторинг (переименование, выделение функций).
- Объяснение кода.
- Простые тесты.

**Плюсы:**

- Бесплатно для физлиц (платно для коммерческого использования).
- Работает в PyCharm без VPN.
- Официальная поддержка Сбера.
- Данные не уходят за рубеж.
- Понимает контекст проекта (если указать `docs/context/`).

**Минусы:**

- Не автономен — не может сам создать файл, запустить тест, сделать миграцию.
- Качество на сложных задачах ниже Claude/Cursor (по отзывам).

**Как настроить:**

1. PyCharm → Settings → Plugins → Marketplace → «GigaCode».
2. Установить, авторизоваться через Сбер ID.
3. Settings → Tools → GigaCode → Project Context → добавить `docs/context/`.
4. Готово.

**Когда использовать:** каждый день, для рутины.

### 15.10.3. Вариант B: Самописный агент на GigaChat API

**Что это:** собственный ИИ-агент на Python, который использует GigaChat API напрямую и умеет:

- Читать файлы (`read_file`).
- Писать файлы (`write_file`).
- Запускать команды (`run_command`).
- Искать по файлам (`search_in_files`).
- Списывать структуру проекта (`list_files`).

**Как работает (цикл think-act-observe):**

```
Задача (task.md)
    ↓
[think] GigaChat анализирует задачу + контекст
    ↓
[act] Агент вызывает инструмент (например, read_file)
    ↓
[observe] Агент получает результат
    ↓
[think] ... и так до завершения задачи или лимита итераций
    ↓
Отчёт: что сделано, что проверено, что осталось
```

**Для каких задач:**

- Автономные задачи, где надо много шагов: создать модель + миграцию + репозиторий + сервис + тесты.
- Рутинные многофайловые изменения.
- Написание тестов по существующему коду.
- Массовый рефакторинг.

**Плюсы:**

- **Полный контроль.** Мы знаем, что агент делает.
- **Безопасность.** Whitelist команд: только `pytest`, `alembic`, `python`, `git status`. Никаких `rm -rf`.
- **Прозрачность.** Логи каждого шага.
- **Автономность.** Может работать часами без участия человека.

### 15.10.5. Про `gpt2giga` — как опция

## 15.11. Самописный ИИ-агент (архитектура и код)

### 15.11.1. Зачем нужен

**Проблема:** GigaCode — не автономен. Он помогает писать код, но не может:

- Создать файл с нуля.
- Запустить `pytest` и проверить результат.
- Сделать `alembic revision --autogenerate`.
- Пройти по нескольким файлам и внести согласованные правки.
- Оформить Pull Request.

**Решение:** собственный ИИ-агент на GigaChat API, который умеет это делать автономно.

**Цель:** автоматизировать **рутинные многошаговые задачи**, чтобы освободить время на архитектуру и сложные фичи.

### 15.11.2. Архитектура (think-act-observe)

Агент работает по классическому циклу **ReAct** (Reasoning + Acting):

```
┌─────────────────────────────────────────────┐
│  Задача (task.md)                           │
│  + docs/context/CONTEXT.md                  │
│  + docs/context/RULES.md                    │
└──────────────────┬──────────────────────────┘
                   ↓
         ┌─────────────────────┐
         │  [think]            │
         │  GigaChat решает,   │
         │  что делать дальше  │
         └─────────┬───────────┘
                   ↓
         ┌─────────────────────┐
         │  [act]              │
         │  Вызов инструмента  │
         │  (read_file, etc.)  │
         └─────────┬───────────┘
                   ↓
         ┌─────────────────────┐
         │  [observe]          │
         │  Результат          │
         │  инструмента        │
         └─────────┬───────────┘
                   ↓
         Задача решена? ──нет──→ вернуться к [think]
                   │
                  да
                   ↓
         ┌─────────────────────┐
         │  Отчёт              │
         │  (что сделано,      │
         │   что проверено,    │
         │   что осталось)     │
         └─────────────────────┘
```

**Ключевые компоненты:**

1. **Оркестратор** (`AgentRunner`) — управляет циклом, следит за лимитами.
2. **GigaChat-клиент** (`GigaChatClient`) — обёртка над GigaChat API.
3. **Инструменты** (`tools/`) — read_file, write_file, run_command, list_files, search_in_files.
4. **Конфиг** (`AgentConfig`) — max_iterations, whitelist команд, разрешённые пути.
5. **Логгер** (`AgentLogger`) — каждый шаг в `docs/tasks/<task_id>/log.md`.

### 15.11.3. Инструменты агента

| Инструмент | Назначение | Аргументы |
|------------|-----------|-----------|
| `read_file` | Прочитать файл | `path`, `start_line?`, `end_line?` |
| `write_file` | Записать файл (перезапись) | `path`, `content` |
| `edit_file` | Точечное изменение | `path`, `old_string`, `new_string` |
| `list_files` | Список файлов в папке | `path`, `pattern?` |
| `search_in_files` | Поиск строки в файлах | `query`, `path`, `file_pattern?` |
| `run_command` | Запустить whitelisted-команду | `command`, `cwd?` |
| `finish` | Задача завершена | `summary` |

**Whitelist команд** (config):

```python
ALLOWED_COMMANDS = [
    "pytest",
    "alembic",
    "python",
    "git status",
    "git diff",
    "git log",
    "ruff",
    "type",  # для Windows
    "dir",   # для Windows
]
```

**Запрещено:** `rm`, `del`, `format`, `git push`, `git commit` (коммит — только человек), любые команды, меняющие состояние вне репозитория.

### 15.11.4. Ограничения и безопасность

**Лимиты:**

- `max_iterations = 30` — если не уложился, агент останавливается и просит помощи.
- `max_tokens_per_task = 100_000` — защита от «сжигания» токенов.
- `timeout_per_command = 300 сек` — долгие команды прерываются.

**Безопасность:**

- **Whitelist команд.** Никаких `rm -rf`, `git push`, `git commit`.
- **Запрет на запись вне репозитория.** Все пути проверяются на префикс `C:\Users\abelo\GIP-Assistant\gip-assistant\`.
- **Plan Mode.** Агент **сначала** пишет план в `plan.md` и ждёт подтверждения человека. Только после `approve` начинает действовать.
- **Логирование.** Каждый шаг пишется в `docs/tasks/<task_id>/log.md` — можно проверить, что агент делал.
- **Без доступа к `.env`.** Файл `.env` в чёрном списке.

**Что агент НЕ делает:**

- Не коммитит (`git commit`).
- Не пушит (`git push`).
- Не трогает секреты (`.env`, `*.key`).
- Не удаляет файлы без явного подтверждения.
- Не работает с БД напрямую (только через `alembic`).

## 16. ГОСТ-совместимость (Уровень 1.5 + roadmap)

### 16.1. Зачем это нужно

**Принцип:** все документы хранятся по нормам. Не «для экспертизы», а как фундамент.

ГИП работает с нами — его данные готовы к СОД, ЕЦПЭ, архиву. Без этого:

- нельзя выгрузить документы в государственную экспертизу,
- нельзя передать проект в архив по правилам,
- нельзя использовать данные в других системах (Vitro-CAD, TDMS).

**Ключевая фраза:**

> Мы не делаем «фичу для экспертизы». Мы строим фундамент, на котором данные ГИПа живут по нормам с первого дня.

### 16.2. Три уровня совместимости

#### Уровень 1 — Хранение (MVP, нед. 3)

**Цель:** документы хранятся по ГОСТ, с правильными метаданными и связями.

**Что делаем:**

- Модель `Document` с ГОСТ-полями (см. раздел 16.5):
  - `cipher` (обозначение), `base_designation`, `section_code`, `mark`
  - `document_kind` (ПД / РД), `doc_part_type` (ТЧ / ГЧ)
  - `document_type_id` (FK на справочник)
  - `lifecycle_status` (DRAFT / IN_REVIEW / NORMOCONTROL / APPROVED / ARCHIVED / ANNULLED / REPLACED)
- Сущность `DocumentVersion` — версии файла:
  - `version` (v1.0, v1.1), `change_number` (Изм. 1, 2, 3 — ГОСТ 7.3.1)
  - `hash_sha256`, `format_original`, `format_archive`, `size_bytes`
  - `is_current` — итоговая версия
- Сущность `DocumentLink` — связи между документами:
  - `link_type`: `appendix`, `reference`, `replaces`, `version_of`
- Справочник `document_types` (FK):
  - чертёж, схема, ПЗ, ведомость, УЛ, ТЗ, спецификация, расчёт
- **GUID документа** — постоянный, не меняется при выпуске новых версий (ГОСТ 8.2.4).
- Метаданные подписи — nullable, без логики:
  - `signed_by`, `signed_at`, `signature_hash`, `signature_status`
- Структура хранения в MinIO:
  - `projects/{project_id}/documents/{document_id}/{version}_{filename}`
  - `projects/{project_id}/xml/{xml_document_id}_{schema_code}.xml`

**Что НЕ делаем на Уровне 1:**

- Валидацию имён файлов по маске ГОСТ (это Уровень 2).
- Автопарсинг имени → `cipher`, `mark`, `stage` (это Уровень 2).
- Формирование ведомостей по формам 1 и 2 (это Уровень 2).

**Сдвиг сроков:** Уровень 1 встраивается в нед. 3 MVP (вместе с MinIO). Пилот сдвигается: **нед. 5 → нед. 6**.

#### Уровень 2 — Формирование (MVP-1.5 + MVP-2)

**Цель:** система формирует документы в формате, готовом к сдаче.

**Что делаем:**

- **Ведомость комплектов рабочих чертежей** (форма 1, ГОСТ Р 21.101-2026).
- **Состав проектной документации** (форма 2).
- **Удостоверяющий лист (УЛ)** — форма 15.
- **Автозаполнение таблицы изменений** в штампе (форма 3–6).
- **Валидация имён файлов** по маске ГОСТ (warning, не блокировка).
- **Автопарсинг имени** → `cipher`, `mark`, `stage`.
- **XML-формирование** ТЗ и ПЗ по схемам Минстроя (см. раздел 16.4).

#### Уровень 3 — Процесс (MVP-4)

**Цель:** интеграция с внешними системами, аудит, долгосрочное хранение.

**Что делаем:**

- **Хранение метаданных о подписи** (полноценное).
- **Интеграция с внешним сервисом ЭП** (УКЭП, УНЭП, МЧД через API).
- **Аудит-лог** — все действия с документами.
- **Долгосрочное хранение** (Приказ Росархива № 77).
- **Интеграция с САПР** (Revit, AutoCAD, nanoCAD).
- **ЦИМ (IFC)** — информационная модель.

### 16.3. Что НЕ делаем сами (и почему)

**УКЭП / УНЭП / МЧД — внешний сервис.**

Это отдельный продукт: криптопровайдер (КриптоПро CSP, VipNet CSP) + удостоверяющий центр + лицензии ФСБ/ФСТЭК. Мы храним только метаданные подписи (`signed_by`, `signed_at`, `signature_hash`, `signature_status`) и интегрируемся по API с внешним сервисом.

**Удостоверяющий лист (УЛ)** — генерируем как PDF/XML, без криптографии. Подписи ставит внешний сервис.

**Долгосрочное хранение** — интеграция с внешним архивом. Приказ Росархива № 77 регулирует формат и сроки, но сам архив — не наш продукт.

**Удостоверяющий центр** — не наш продукт.

**Криптопровайдеры** — не наш продукт (лицензии ФСБ/ФСТЭК).

### 16.5. Модель Document (ГОСТ Р 21.101-2026 + Docsvision)

#### 16.5.1. Сущности (SQL-схема)

**4 таблицы:**

```sql
-- document_types (справочник)
CREATE TABLE document_types (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code VARCHAR(50) NOT NULL UNIQUE,
    name VARCHAR(200) NOT NULL,
    description TEXT,
    gost_code VARCHAR(50),  -- код по ГОСТ (например, "ПЗ", "АР")
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- documents (карточка документа)
CREATE TABLE documents (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    guid UUID NOT NULL UNIQUE,  -- постоянный, не меняется при версиях
    project_id UUID NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    entity_id UUID REFERENCES entities(id) ON DELETE SET NULL,
    task_id UUID REFERENCES tasks(id) ON DELETE SET NULL,

    -- Обозначение (ГОСТ Р 21.101-2026, 4.1, 4.2)
    cipher VARCHAR(500) NOT NULL,
    base_designation VARCHAR(200),
    section_code VARCHAR(50),
    document_kind VARCHAR(10),  -- ПД / РД
    mark VARCHAR(50),
    doc_part_type VARCHAR(10),  -- ТЧ / ГЧ (новое в 2026)

    -- Наименование
    document_name VARCHAR(500) NOT NULL,
    document_type_id UUID NOT NULL REFERENCES document_types(id),

    -- Версионность
    current_version_id UUID,
    version_parent_id UUID REFERENCES documents(id),
    replaces_id UUID REFERENCES documents(id),
    replaced_by_id UUID REFERENCES documents(id),

    -- Жизненный цикл
    lifecycle_status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',

    -- Подпись (метаданные)
    signed_by UUID REFERENCES users(id),
    signed_at TIMESTAMPTZ,
    signature_hash VARCHAR(255),
    signature_status VARCHAR(50),

    -- Служебные
    created_by UUID REFERENCES users(id),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_documents_project ON documents(project_id);
CREATE INDEX idx_documents_entity ON documents(entity_id);
CREATE INDEX idx_documents_task ON documents(task_id);
CREATE INDEX idx_documents_guid ON documents(guid);
CREATE INDEX idx_documents_type ON documents(document_type_id);
CREATE INDEX idx_documents_status ON documents(lifecycle_status);

-- document_versions (версии файла)
CREATE TABLE document_versions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    version VARCHAR(20) NOT NULL,  -- v1.0, v1.1, v2.0
    change_number INT,  -- Изм. 1, 2, 3 (ГОСТ 7.3.1)
    file_path VARCHAR(1000) NOT NULL,
    file_name VARCHAR(500) NOT NULL,
    hash_sha256 VARCHAR(64) NOT NULL,
    format_original VARCHAR(20) NOT NULL,
    format_archive VARCHAR(20),
    size_bytes BIGINT NOT NULL,
    is_current BOOLEAN NOT NULL DEFAULT FALSE,
    uploaded_by UUID REFERENCES users(id),
    uploaded_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(document_id, version)
);

CREATE INDEX idx_document_versions_document ON document_versions(document_id);
CREATE INDEX idx_document_versions_current
    ON document_versions(document_id, is_current)
    WHERE is_current = TRUE;

-- document_links (связи между документами)
CREATE TABLE document_links (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    target_document_id UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    link_type VARCHAR(30) NOT NULL,  -- appendix / reference / replaces / version_of
    created_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(source_document_id, target_document_id, link_type)
);

CREATE INDEX idx_document_links_source ON document_links(source_document_id);
CREATE INDEX idx_document_links_target ON document_links(target_document_id);
```

### 16.8. Риски и открытые вопросы

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| ГОСТ Р 21.101-2026 обновится | Средняя | Отслеживать `rst.gov.ru`, поправка от 27.08.2026 учтена |
| Модель Document «поплывёт» при MVP-1.5 | Средняя | `DocumentVersion` + `DocumentLink` заложены сразу |
| Справочники (`marks`, `stages`, `document_types`) не успеем | Низкая | Enum в коде для MVP, таблицы — в MVP-2 |
| XML-схемы Минстроя обновятся | Высокая | Кэш в БД + автопроверка при каждом экспорте |
| GUID генерируется неправильно (UUIDv4 vs UUIDv5) | Низкая | UUIDv4 в приложении (контроль), не в БД |
| `is_current` не переключается при новой версии | Средняя | Триггер или логика в сервисе |
| Валидация имён файлов по ГОСТ — warning или блокировка? | Средняя | Warning (ГИП может переименовать позже) |
| Структура MinIO по ГОСТ — обязательна для старых загрузок? | Низкая | Только для новых, старые — миграция в MVP-2 |

**Открытые вопросы:**

1. **Справочники (`marks`, `stages`) — таблицы или enum?**
   - Для MVP: **enum в коде** (быстрее, без миграций).
   - Для MVP-2: **таблицы** (редактирование без деплоя).

2. **Валидация имён файлов — warning или блокировка?**
   - **Warning.** ГИП может загрузить «грязный» файл и переименовать позже.

3. **Структура MinIO по ГОСТ — обязательна или опция?**
   - **Обязательна для новых загрузок.** Старые — не трогаем (миграция в MVP-2).

4. **GUID — UUIDv4 или UUIDv5?**
   - **UUIDv4** (случайный) — генерируется в приложении, не в БД. Контроль + тестируемость.

5. **XML-схемы Минстроя — у тебя есть актуальные редакции?**
   - Есть 3 схемы (ПЗ, ТЗ, сметная ПЗ) + XSL + PDF.
   - На MVP-1.5 — используем их.
